# 결정 기록

개발자가 확정한 결정과 이유. 바뀐 결정은 해당 절을 고치고, 새 결정은 절을 더한다. 경로는 분석 대상 저장소의 루트 기준이다.

## 문제 상황

문서도, 인수인계해 줄 사람도 없이 마이크로서비스 프로젝트를 넘겨받는다. 넘겨받는 사람이 가진 것(저장소, 떠 있다면 서버)만으로 확인할 수 있는 것과 없는 것을 근거와 함께 보여 주는 도구를 만든다. 넘겨받는 상황은 둘이고, 결과를 받는 쪽과 창구가 다르다.

| | 서비스가 떠 있고 문서가 없음 | 저장소만 남음 |
|---|---|---|
| 쓰는 사람 | 서비스 API를 쓰는 사람과 에이전트. 코드를 갖지 않았거나 읽지 않는다 | 서비스를 되살릴 개발자. 저장소를 가졌다 |
| 필요한 것 | API 스펙과 서비스 사이 흐름, 각각 어디까지 확인됐는지 | 띄우는 데 필요한 환경변수·외부 자원, 이어지지 않는 연결, 함정 |
| 창구 | 문서 페이지, 질의응답, MCP | 문서 페이지(띄우는 데 필요한 것을 모은 되살리기 페이지 포함) |

분석은 두 상황이 같다. 저장소를 읽어 추출하고, 서버가 떠 있으면 응답으로 확인해 확인 범위를 가른다. 저장소를 가진 사람과 에이전트는 코드를 직접 읽을 수 있으므로 MCP는 저장소 없이 API를 쓰는 쪽을 위한 창구다.

HotDealWave는 저장소만 남은 경우다. 서비스가 떠 있는 경우는 고정 커밋을 띄워 시험한다.

다루는 범위는 근거가 어디 있는지로 가른다. 저장소 안에 근거가 있는 것은 API든 배포·운영 설정이든 근거 `파일:줄`과 상태를 붙여 내고, 저장소 밖에만 있는 것(콘솔 설정, 등록된 시크릿 값, 운영 접속 대상)은 "저장소에 근거 없음"으로 밝힌다. 프론트엔드·백엔드나 API·운영으로 가르지 않는다. #45 때는 배포 워크플로, 모니터링 설정, 오류 응답을 아직 뽑지 않았다. 범위 밖이 아니라 아직 뽑지 않은 것이었고, 오류 응답은 #47, 배포·모니터링은 #49에서 뽑았다.

## 결과물 세 가지

| 결과물 | 쓰는 쪽 | 답을 만드는 모델 |
|---|---|---|
| 문서 페이지 | 사람이 읽음 | 없음 |
| 검색·질의응답 페이지 | 사람이 질문 | 서버가 호출(고정 RAG) |
| MCP | API를 쓰는 쪽의 Claude Code·Codex | 클라이언트의 모델 |

세 결과물을 Spring Boot 서버 하나가 제공한다. 로컬에서도 같은 서버 하나를 띄우고, 배포할 때도 그 서버 하나를 올린다.

## 도구와 평가

도구는 대상 저장소마다 사람의 질문·채점 없이 돈다. AI 추출, 검증, 서버가 전부다. 검증 경고는 판정 없이 "확인 안 됨"으로 보여 준다.

평가는 이 도구가 실제로 돕는지를 HotDealWave에서 한 번 잰다([비교 실험](#비교-실험)). 두 번째 대상에는 최종 질문·채점 없이, 처음 쓰는 사람의 순서로 도구를 끝까지 써 보고 막힌 곳과 검증 경고를 본다. 질의응답 검색은 조정용 질문으로 근거가 모델에 넘기는 상위 8개에 드는지만 확인한다.

## 사용 범위와 흐름

HotDealWave로 만든 도구를 다른 저장소에서도 쓸 수 있도록 범위와 흐름을 정했다. 10단계를 준비하며 두 모델이 따로 설계안을 쓰고 서로 비판한 뒤 별도로 판정했다.

- 추출은 Spring Boot·Spring Cloud MSA만 다룬다. 흔한 Spring 구성(Maven, `application.properties`·`application.yaml`, `build.gradle.kts`, 하위 폴더의 서비스)은 읽는다. 다른 스택과 모놀리식은 Skill과 검증 규칙을 더해 넓힌다. 그때까지는 다른 구성에 맞추려면 고칠 곳을 README에 표로 둔다.
- 도구와 대상을 떼어 낸다. 사용자는 대상 저장소(경로 또는 주소)와 커밋, 작업 폴더를 준다. 도구가 작업 폴더 안에 복제해 그 커밋으로 고정하고, 추출 결과와 검증 출력도 그 작업 폴더에 둔다. 사용자 체크아웃과 도구 저장소는 바뀌지 않는다.
- 명령은 jar 하나를 `java -jar`로 부르는 `init`, `verify`, `serve` 세 개다. OS마다 다른 실행 파일을 두지 않는다. 사람은 대상을 받는 `init`과 결과를 보는 `serve`만 치고, `verify`는 AI가 추출을 마칠 때 부른다. `serve`는 검증하지 않고 `out/analysis.json`만 읽는다. 대상 코드가 없는 곳에 결과만 올려 띄울 수 있어야 하기 때문이다.
- 사용자의 AI 세션은 작업 폴더에서 연다. `init`이 거기에 이 대상 전용 지시 파일(대상 코드와 Skill 파일의 위치, 추출 순서, 마칠 때 `verify`)을 쓰고, 다음 할 일은 AI가 이 순서와 작업 폴더의 파일을 보고 정한다. 서비스별 추출은 서로 독립이라 세션을 나눠 동시에 돌릴 수 있다. 도구 저장소의 루트 지시 파일과 이슈·PR Skill은 도구 개발용으로 둔다. 도구 저장소에서 세션을 열면 사용자 세션이 개발 규칙을 읽고, 결과를 쓸 작업 폴더를 세션에 따로 더해야 하기 때문이다.
- 사용자에게 필요한 것은 JDK, Git, 코딩 에이전트 하나(Claude Code 또는 Codex)다. 질의응답을 쓰려면 OpenAI 키 하나가 더 든다.
- 결과물 세 가지(문서 페이지, 검색·질의응답, MCP)를 모두 둔다. 질의응답은 검색을 BM25와 임베딩의 RRF로 바꿔 품질을 올린다([검색](#검색)).
- "저장소만 남음" 상황을 위해 띄우는 데 필요한 것(외부 자원, 채워야 할 환경변수, 저장소 밖 비밀값, 컨테이너, 띄울 때 확인할 연결, 운영 함정, 도구가 다루지 않은 위치)을 한 페이지에 모은다. 새로 뽑지 않고 있는 데이터를 모은다. 모든 절이 다른 페이지의 반복이라 검색·질의응답 색인에는 넣지 않고 MCP `get_page`로만 읽는다(#68). 이 페이지만 보고 두 번째 대상을 띄워 막힌 곳을 기록하는 측정은 MVP에서 하지 않았다. 대상의 DB·외부 API 키를 직접 준비해야 해서, SpartaHub 결과로 페이지가 내는 내용까지만 확인했다.
- 서비스 간 통신 형식의 일반화는 MVP에 포함한다(#62). 지원 기준은 특정 분석 대상이 아니라 Spring이 제공하는 서비스 간 통신 방식이다. HTTP 호출은 OpenFeign·RestTemplate·RestClient·WebClient·HTTP 인터페이스, 메시지는 Kafka·RabbitMQ·Spring Cloud Stream을 다룬다. 역할 배열과 `kind`로 표현하고 선언 줄 규칙을 한 곳에 모아, 새 방식을 추가해도 서버 흐름을 바꾸지 않는다. gRPC·GraphQL·WebSocket과 회로 차단기 fallback은 이번 범위 밖이다.
- 인수인계 뒤 대상이 바뀌었을 때 고쳐 가는 일(증분 재분석)은 다루지 않는다.

## 구조

```
작업 폴더의 대상 @고정 커밋 --> AI 추출(Skill) --> 작업 폴더의 services/*.json + relations.json + repository.json
떠 있는 서버(있을 때) -----------> AI 호출(Skill) --> 작업 폴더의 responses/ (관찰 기록)
추출 결과에서 코드·응답으로 --> AI 해석(Skill) --> 작업 폴더의 knowledge/*.json <-- 개발자의 경고 판정

services/*.json + relations.json + repository.json --+
knowledge/*.json (있을 때) --------------------------+--> verifier (verify)
                                                        |
                                                        v
                                               out/analysis.json (추출·항목·상태·경고)
                                                        |
                                                        v
                                      server (Spring Boot, 하나의 프로세스)
                                        +-- 조회: 관계 조회 3개 + 검색(BM25)
                                        +-- 페이지: 문서·검색·질문 (Thymeleaf)
                                        +-- /api/search, /api/ask
                                        +-- /mcp  <-- Claude Code·Codex (HTTP)
```

- `verifier`와 `server`는 같은 Gradle 프로젝트의 모듈이고, `out/analysis.json` 하나로만 연결한다. 세 명령은 `cli` 모듈이 두 모듈을 jar 하나(`build/handover.jar`)로 묶어 낸다. 스키마는 양쪽 테스트가 확인한다.
- 업무 규칙·함정도 검증기가 작업 폴더의 `knowledge/*.json`을 검사해 같은 출력의 `knowledge` 배열에 합친다. 항목 디렉터리가 없으면 기존 출력과 같다.
- 조회 계층은 관계 조회 3개(`find_endpoint`, `trace_flow`, `find_subscribers`)와 `search_docs`(BM25)를 제공하고 모델을 부르지 않는다. 페이지, API, MCP가 모두 이 계층을 쓴다.
- `/mcp`는 조회 계층을 MCP 도구로 그대로 노출한다(Streamable HTTP, 요청마다 독립인 무상태 방식). 도구는 관계 조회 3개, `search_docs`, 페이지 본문 전체를 읽는 `get_page`이고, 결과는 페이지 본문과 같은 텍스트다. 답은 클라이언트의 모델이 쓴다. 서버 안에서 모델을 부르는 도구는 두지 않는다.
- `/api/ask`는 고정 RAG다. 항상 검색을 한 번 하고([검색](#검색)의 BM25·임베딩 RRF), 모델을 한 번 부르고, 인용을 검사해 답하거나 보류한다. 질문당 호출 수가 정해져 있어 비용을 미리 말할 수 있고, 같은 질문으로 다시 재기 쉽다. 흐름을 여러 단계로 따라가는 질문은 MCP 경로가 맡는다.
- 답은 인용 검사를 통과한 뒤 한 번에 보여 준다. 스트리밍은 하지 않는다. 화면에 먼저 나간 답은 검사할 수 없기 때문이다.
- 질문은 하나씩 받는다. 대화 기록을 넘기면 "그럼 결제는?" 같은 후속 질문에서 검색이 빗나가고, 채점도 질문 단위로 해야 하기 때문이다.
- 모델에는 검색 상위 8개를 C1~C8로 넘긴다. 엔드포인트·토픽 페이지는 찾은 절 대신 본문 전체를 넘긴다. 필드 질문이 이름·설명 절에 걸려도 요청·응답 필드가, 연결 질문이 설명 절에 걸려도 발행·구독 연결의 확인 상태가 함께 가야 하기 때문이다(#37). 입력은 질문 한 번에 평균 약 4만 6천 토큰이다(#63 재실행).
- 모델 키는 `OPENAI_API_KEY` 환경변수에서 읽는다. 키가 없어도 서버는 뜨고 질문만 오류로 답한다.

## 검색

- 조각은 엔드포인트·토픽·서비스·배포·모니터링(`/repository`) 본문의 `h2` 절이다. 되살리기 페이지는 다른 페이지의 반복이라 색인하지 않는다. 페이지와 검색은 같은 템플릿으로 렌더링한 본문을 쓴다. 근거 링크·접기와 상태 색은 브라우저에 보낼 때만 덧씌워, 검색·MCP·모델이 읽는 본문 글자는 바뀌지 않는다(#39).
- 질문에 서비스 이름(`order-service`, `order` 등)이나 종류(API, 토픽, 설정 등)가 나오면 그 서비스·종류의 조각만 먼저 찾는다. 결과가 없으면 필터를 하나씩 풀어 다시 찾는다. 서비스는 `analysis.json`의 서비스 이름과 디렉터리 이름이 질문의 낱말과 통째로 같을 때만 거르고, 종류 말은 대상과 상관없는 고정 목록이다.
- 같은 페이지의 조각은 점수가 가장 높은 하나만 남기고 상위 5개를 고른다. 질의응답은 상위 8개를 넘긴다. 5개로는 RRF에서 T03의 BM25 2·4위 근거가 밀렸다(#63).
- 토큰화는 식별자를 통째로, 점·하이픈으로 이은 이름은 그 안의 식별자도 통째로, camelCase·snake_case 단위로도 나누고, 한국어는 두 글자씩 자른다. 두 글자는 조사가 붙어도 같은 말이 남게 하려고 rag-chatbot의 방식을 옮긴 것이고, 형태소 분석기와 비교하지는 않았다.
- 질의응답(`/api/ask`)의 검색은 BM25 순위와 임베딩 순위를 RRF(순위만으로 합치기, 상수 60)로 합친다. 조정용 질문에서 BM25가 표현 차이로 근거를 놓쳤기 때문이다(#53의 T04). 임베딩은 OpenAI API(`text-embedding-3-large`)로 절마다 한 번 만들어 작업 폴더에 두고, 질문마다 한 번 만든다. 입력 한도를 넘는 긴 절은 3천 자 조각으로 나눠 가장 가까운 조각의 유사도로 순위를 매긴다. 하이브리드가 BM25가 못 찾던 근거를 하나 이상 찾고 BM25가 찾던 것을 하나도 잃지 않을 때 채택한다. #63에서 조정용 질문 T03~T10의 결과가 갈린 절을 Codex·Opus가 따로 판정하고 갈린 판정은 개발자가 정했다. RRF 상위 8개가 새 근거 13개를 찾고 잃은 근거가 없어 채택했다. BM25 1위였다가 빠진 T06의 `product-dlq` 절은 재시작·종료·준비 상태에 관한 사실이 없어 근거가 아니다(#53에서 1위로 들어갔을 때도 답은 보류였다). T06에 필요한 재시작 관련 사실은 문서에 없어 추출 범위의 과제다. MCP의 `search_docs`는 클라이언트 모델이 검색어를 바꿔 여러 번 찾을 수 있어 BM25로 둔다.

## 언어와 라이브러리

| 부분 | 선택 | 이유 |
|---|---|---|
| 추출 | AI 세션(Claude Code·Codex)과 Skill | 프레임워크가 달라도 지시문으로 따라간다. 세션 작업이라 별도 유료 호출이 없다 |
| 검증 | Java 17, SnakeYAML, Jackson, JSON Schema Validator | 서버와 같은 실행 환경이다. 추출의 확인 상태는 검증기가, 업무 규칙·함정의 확인 상태는 개발자가 정한다 |
| 서버 | Spring Boot, Thymeleaf | 검증과 같은 실행 환경 하나로 빌드·테스트·배포한다. 개발자가 직접 읽고 판단할 수 있는 스택이다. 화면 모양은 중요하지 않다. 흐름은 그림 라이브러리 없이 본문의 단계 줄을 CSS로 잇는다 |
| MCP | MCP Java SDK(`mcp-core`의 서블릿용 Streamable HTTP 전송) | Spring Boot에 바로 붙는다. Claude Code·Codex 모두 HTTP 방식 MCP를 등록할 수 있어 표준 입출력 방식은 두지 않는다 |
| 질의응답 | OpenAI Java SDK(정해진 형식의 출력) | rag-chatbot의 방식(BM25, 정해진 형식의 답·인용·보류, 보류 규칙)을 옮긴다. 인용 검사는 답의 `파일:줄`이 인용한 조각에 있는지까지 본다. 모델은 `gpt-6-luna`(추론 없음, 출력 1500토큰 상한)다. 입력 100만 토큰당 0.10달러로 질문 한 번에 1센트 아래다 |

## 배포

배포는 선택이다. 하게 되면 서버 하나를 손으로 올리고 CD는 붙이지 않는다. `out/analysis.json`은 이미지를 만들 때 넣는다. `/api/ask`는 하루 호출 상한을 두고, 모델 키는 배포처의 비밀값으로 둔다. 원격 `/mcp`는 공개 저장소를 분석한 읽기 전용 데이터라 인증 없이 연다.

## 분석 대상: 원본 저장소의 `cc43016`

팀 원본 저장소(`sparta-final-12th-9700/HotDealWave`)의 main 끝 커밋(2025-01-24)이다. 새로 온 사람이 받는 것은 팀 원본이므로 그 상태를 그대로 분석한다. 원본에 접근할 수 없게 되면 같은 커밋을 가진 포크로 `target.json`의 주소만 바꾼다. 처음에는 이 저장소의 서브모듈로 고정했지만, 다른 대상을 쓰려면 도구 저장소를 고쳐야 해서 다른 대상과 같은 방식(작업 폴더에 복제)으로 바꾼다. HotDealWave 결과는 예시로 남긴다.

두 번째 대상은 개발자의 공개 저장소 하나다. 커밋을 고정하고 같은 도구를 돌려, 다른 저장소에서 어디까지 되는지 본다.

## 추출 방식

AI 세션이 Skill을 따라 대상 코드를 읽고 [정해진 형식](format/README.md)으로 쓴다. 항목마다 근거 `파일:줄`을 붙인다. 결과는 작업 폴더에 쓴다. HotDealWave 결과는 다시 만들 수 없어 예시 작업 폴더(`examples/hotdealwave/`)로 커밋한다. 그 검증 출력(`out/analysis.json`)도 커밋해, 도구를 받은 사람이 `init` 없이 `serve`로 예시를 보고 서버 테스트가 대상 코드 없이 돈다. 검증기 테스트가 커밋된 출력이 지금 검증기로 다시 만든 것과 같은지 확인한다.

서비스 파일은 작업 폴더의 `services/<spring.application.name>.json`, 메시지 연결과 핸들러의 나가는 호출은 `relations.json`에 둔다. 서비스 파일에는 서비스 하나와 그 서비스의 추출 배열을 담고, 관계 파일에는 `messageLinks`, `calls`, `throws`를 담는다. 서비스 하나에 속하지 않는 배포 워크플로·서비스 이미지·모니터링 설정은 `repository.json`에 둔다(#49). 다른 저장소에도 쓰도록 배열은 도구 이름이 아니라 역할(배포 파이프라인, 컨테이너, 메트릭 수집, 로그 전송, 도구 자체 설정, 모니터링 도구)로 나누고, 도구 이름은 항목의 값으로 둔다(#51). 대상 이름, 원본 저장소 주소, 고정 커밋은 `target.json`에 두어 서버가 대상마다 고쳐지지 않게 한다(#54). `calls`는 엔드포인트·Kafka 구독에서 같은 서비스의 Feign 호출·발행까지 이어지는 연결이다. 넘겨받는 사람이 "이 API를 부르면 어디까지 이어지는가"를 따라가려면 필요하고, 이미 응답 비교를 거친 서비스 파일을 다시 추출하지 않으려고 관계 파일에 둔다. 검증기는 스키마 검사 뒤 합쳐 `out/analysis.json` 하나를 낸다.

업무 규칙·함정은 별도 `rules-msa-java-spring` Skill로 추출 결과에서 출발해 코드와 저장된 응답을 읽고 작업 폴더의 `knowledge/<spring.application.name>.json`에 쓴다. 관계 추출 형식은 그대로 두고, 검증기가 항목도 같은 출력에 합친다.

ID는 애플리케이션 이름으로 시작한다(엔드포인트·Feign·Kafka). ID 앞부분으로 `services/<spring.application.name>.json`을 찾을 수 있게 하며, 게이트웨이 경로 ID처럼 대상 코드에 적힌 값은 그대로 쓴다. `service` 필드가 없는 항목은 근거 경로가 `service.directory`로 시작하는 서비스에 속하고, 정할 수 없으면 멈추고 보고한다. 서비스가 하위 폴더(`services/order`)에 있어도 같다.

형식에 담을 자리가 없는 방식(예: gRPC 호출, 회로 차단기 fallback)은 항목으로 만들지 않고, 위치와 방식 이름, 한 줄 설명을 `unsupported` 배열에 남긴다. 완료 보고에만 남기면 결과를 보는 사람은 그 서비스의 흐름이 완전한지 알 수 없다. 페이지와 흐름 결과에는 그 서비스에 도구가 다루지 않는 방식이 있다고 한 줄로 붙인다.

지금은 MSA만 다룬다. 모놀리식은 나누는 단위를 도메인으로 바꾼 별도 Skill로 대응한다.

파서 추출기는 3단계에서 HotDealWave의 AI 추출 결과와 대조하는 기준선으로 썼다.

## Kafka 연결 규칙

DLQ 발행 두 곳(문자열 `payment-dlq`·`product-dlq`)을 빼면 토픽 이름은 코드와 설정 어디에도 값으로 없다. `@Value("${spring.kafka.topics.x}")` → `application.yml`의 `${KAFKA_..._TOPIC}` → `docker-compose.yml`의 `${KAFKA_..._TOPIC}`으로 이어지고, 값은 배포 서버의 환경에서 들어온다(`.github/workflows/actions.yml`이 EC2에서 `docker-compose`를 실행).

- 발행 쪽과 구독 쪽이 같은 환경변수 이름을 쓰면 연결한다. 한 compose 파일 안의 같은 `${변수}`는 같은 값으로 채워지기 때문이다. 근거는 양쪽 서비스의 compose 줄이다.
- 토픽 이름이 코드나 설정 파일에 값으로 적혀 있고 양쪽이 같으면 연결한다. 같은 이름은 같은 토픽이기 때문이다. 근거는 양쪽의 토픽 이름 줄이다(#58). HotDealWave에서는 문자열 토픽(DLQ 두 곳)을 구독하는 곳이 없어 이 연결이 없다.
- 이름이 다르면 "확인 안 됨"으로 둔다. 이름·필드명·로그 문구가 비슷해도 후보로 내지 않는다.
- 실제 값은 쓰지 않는다. 저장소만 받은 사람은 그 값을 알 수 없다.

## 따라가는 범위

추출이 따라가야 하는 HotDealWave의 패턴이다. 사슬의 줄마다 근거를 붙이고, 근거가 끊긴 값은 "확인 안 됨"이다.

| 패턴 | 예 |
|---|---|
| private 래퍼 | `order/.../OrderEventProducer.java:37` → `:62`의 `kafkaTemplate.send` |
| 토픽이 인자로 여러 번 전달됨 | `product/.../ProductKafkaConsumer.java:48` → `:85` → `ProductInventoryService.java:125` → `ProductKafkaProducer.java:14` |
| `send` 없는 DLQ 발행 | `order/.../ConsumerApplicationKafkaConfig.java:61`의 `DeadLetterPublishingRecoverer` |
| 게이트웨이 경로 | `gateway/src/main/resources/application.yml`의 `lb://` 경로 규칙 |
| Feign `name` → 대상 서비스 컨트롤러 | `order/.../ProductClient.java:26`(메서드 `reduceQuantity`, 경로 `/restore-quantity`) |
| 코드에 박힌 외부 URL | `payment/.../KakaoPayClient.java:14` |

## 설정과 외부 자원

서비스를 다시 띄우는 데 필요한 것을 뽑는다. 서비스마다 쓰는 환경변수 이름, 외부 자원(DB, Redis, Elasticsearch, Kafka, S3, KakaoPay)과 그것을 쓰는 코드·설정의 `파일:줄`이다. 환경변수 값과 버킷 이름은 "저장소에 근거 없음"이다.

## API 요청·응답

엔드포인트마다 HTTP 메서드와 전체 경로, 파라미터 종류(경로·쿼리·본문), 요청·응답 DTO의 필드 목록과 클래스 위치까지 뽑는다. API 스펙을 묻는 질문에 필드로 답해야 하기 때문이다.

프론트 개발자가 API를 붙일 때 필요한 것도 함께 뽑는다. 게이트웨이 기준 외부 경로, 필드의 검증 어노테이션(`@NotNull` 등), 필드의 실제 JSON 이름, 게이트웨이에서 토큰이 필요한지(HotDealWave는 `gateway/.../filter/AllowedPath.java`)다. Swagger는 서비스를 띄워야 보이고 설명도 거의 없다.

오류 응답도 뽑는다(#47). 서비스의 오류 코드 enum, 예외 처리기의 상태·본문, 엔드포인트에서 던지는 예외(`relations.json`의 `throws`), Gateway가 본문 없이 끝내는 거부 응답, 페이지 직렬화 설정이다. 프론트 개발자는 정상 응답만큼 실패했을 때 받는 상태·코드·메시지를 묻는다. 9단계에서 맞음이 아닌 답의 일부가 여기에 몰렸다. HotDealWave에는 추출 Skill에 다시 쓸 절만 지정해 새 절만 채웠다. 기존 절을 다시 추출하면 응답 비교와 업무 규칙 참조를 다시 맞춰야 하기 때문이다(개발자 선택).

## 검증

사람이 미리 정답표를 쓰지 않는다. 넘겨받는 사람도 구조를 다 알지 못한 채 시작하기 때문이다. 대신 추출 결과를 대상 저장소의 코드 자체와 비교해, 어긋나는 곳을 경고로 낸다.

| 검증 | 보는 것 | 어긋나면 |
|---|---|---|
| 스키마 | 서비스·관계·업무 규칙·함정 파일의 필수 필드·타입·허용 값이 맞는가 | `schema` 경고 |
| 추출 근거 줄 | 근거 `파일:줄`이 고정 커밋에 있고, 그 줄에 추출 항목의 경로·토픽·필드 이름이 있는가 | 그 추출 항목은 "확인 안 됨" |
| 선언 목록 | 정규식으로 센 선언(`@*Mapping`, `@FeignClient`, `@KafkaListener`, `send`) ↔ 추출 항목. 주석 안의 선언은 세지 않는다 | 빠뜨린 선언 경고 |
| 관계 | 호출 대상 엔드포인트, 발행↔구독 환경변수 이름, 게이트웨이 경로가 결과 안에서 맞는가 | 끊긴 관계 경고 |
| 핸들러 호출 | `calls`의 출발·도착 ID가 있고, 첫 근거가 출발 항목의 첫 근거, 마지막 근거가 Feign 메서드 호출 줄 또는 발행 항목의 첫 근거(`send` 줄)이고, 발행이면 사슬에 그 발행만의 근거 줄이 있는가. 어느 `calls`의 도착도 아닌 Feign 호출·`kafkaTemplate.send` 발행이 있는가 | 그 연결은 "확인 안 됨", `handler-calls` 경고 |
| 업무 규칙·함정 근거 | 고정 커밋의 대상 파일 또는 작업 폴더의 `responses/` 파일에 해당 줄이 있는가 | `knowledge-evidence` 경고, 확인 상태 유지 |
| 업무 규칙·함정 영향 ID | 엔드포인트·Feign 호출·Kafka 발행·구독의 ID가 추출 결과에 있는가 | `knowledge-affected-ids` 경고, 확인 상태 유지 |
| 업무 규칙·함정 중복 | 서비스가 다른 AI 해석 항목끼리 영향 ID 목록이 같은가 | `knowledge-duplicates` 경고, 확인 상태 유지 |

검증을 모두 통과한 추출 항목만 "확인됨"이다. 값이 `${ENV}`로만 나오는 추출 항목은 "저장소에 근거 없음"이다. 선언 패턴은 프레임워크별로 두고, 지금은 Spring 하나다. 추출 검증 규칙은 특정 대상의 작성 방식에 묶지 않고 "근거 줄에 이름이 있는가" 수준으로 둔다. 업무 규칙·함정은 근거 줄의 존재만 검사하며 설명과 줄 내용을 대조하지 않는다. 설명이 맞는지와 확인 상태는 개발자가 정한다.

MCP 비교 실험(9단계)까지는 검증 규칙을 더하지 않고, "확인됨"이 실제로 가르지 못하는 경우만 고친다.

검증기는 남긴다(2026-11-05). 추출이 실행마다 흔들려도 코드와 맞는 값만 "확인됨"이 되고, 1차 추출의 체계적 표기 오류를 한 번에 드러냈기 때문이다. 답의 정확도에 얼마나 기여했는지는 검증기 없는 조건으로 잰 적이 없다. 다음을 고친다.

- 작업 폴더의 대상 코드가 `target.json`의 커밋이 아니거나 바뀐 파일이 있으면 멈춘다.
- "확인됨"이 무엇을 확인했는지 배열마다 한 줄로 정해 도움말과 MCP 결과에 둔다. 호출 사슬은 출발·도착 줄만 보고, 지금은 응답 근거의 줄 내용을 보지 않는다. 응답 근거도 그 줄에 이름이 있는지 보게 한다.
- 경고마다 이유 코드를 붙이고, 코드마다 사용자가 할 일 한 줄을 정한다. 검사 이름만으로는 원인이 갈리지 않는다(예: `kafka-topics` 11개 가운데 DLQ 2개는 저장소 밖 값과 상관없이 끊긴 연결).
- 사용자에게 경고를 판정하거나 다시 추출하게 하지 않는다. 경고는 "확인 안 됨"과 이유로 결과에 나오고, 할 일은 첫 화면과 되살리기 페이지의 점검 항목으로 보여 준다. 다시 추출하는 것은 도구를 고치는 사람의 일이다.
- 페이지는 "확인됨"을 따로 표시하지 않고, 확인되지 않은 값에만 상태와 접은 이유를 붙인다.

경고 판정은 선택이다. 5단계에서 저장소의 코드·응답만으로 결과가 정해지는 경고만 판정해 `eval/facts.csv`에 남긴다. 형식은 [eval/README.md](../eval/README.md). 경고를 없애려고 Skill이나 검증 규칙을 바꾸지 않는다.

## 배포된 서비스 응답 검증

서버가 떠 있으면 실제 응답을 관찰 기록으로 남긴다. 추출과 실제 응답이 다르면 서비스 파일을 고치지 않고, 코드에서 읽은 값과 관찰한 값을 함께 보여 준다. 떠 있는 서버가 분석한 커밋과 같은 버전이라는 보장이 없기 때문이다(2026-11-05, 그 전에는 응답을 따라 고쳤다. 4단계에서 이 규칙으로 고친 항목은 0개였다). 서버가 없으면 이 단계를 건너뛴다. 서비스가 내려간 프로젝트는 사실상 버려진 것에 가까워, 그때는 정적 분석 말고는 방법이 없다.

처음에는 넘겨받는 상황을 고려하지 않고, 품질을 올리려고 로컬에 남은 설정 파일과 기억으로 경고를 판정하려 했다. 넘겨받는 사람은 그것을 갖지 못하므로, 서비스를 띄워 실제 응답으로 확인하는 방식으로 바꿨다.

- 넘겨받는 사람이 가진 것만 쓴다: 서버 주소와 테스트 계정. `.env`, 로컬 설정, 브로커 직접 접근으로 판정하지 않는다.
- AI 세션이 Skill을 따라 로그인하고, 조회 API 전부와 테스트 데이터로 부를 수 있는 쓰기 API를 부른다. 응답 JSON은 엔드포인트별로 작업 폴더의 `responses/`에 저장하고, 토큰과 비밀번호는 저장하지 않는다. 테스트 환경에만 쓴다.
- `verify`가 저장된 응답의 키와 추출한 응답 필드의 JSON 이름을 비교해 엔드포인트의 응답 기록에 "응답에만 있음", "추출에만 있음", "이름 다름"을 붙인다. 처음에는 Python 스크립트였으나, 사용자에게 JDK 말고 Python이 더 들어 검증 단계로 옮겼다(#60).
- 비교 결과로 서비스 파일을 고치지 않는다. 차이는 엔드포인트 페이지에 코드 값과 관찰 값으로 나란히 나온다. 추출에만 있는 필드는 응답에 빠진 이유를 코드에서 찾아 적는다.
- 호출하지 못한 엔드포인트는 이유와 함께 남긴다.
- 검증기는 응답 파일을 엔드포인트마다 `out/analysis.json`에 붙인다(응답 기록 있음과 HTTP 코드 / 호출 못 함과 이유 / 응답 파일이 없으면 코드만, 원문은 줄 번호대로). 서버가 이 출력 하나만 읽으므로 페이지와 업무 규칙·함정의 응답 근거가 여기서 원문을 찾는다. 응답 기록은 확인 상태를 바꾸지 않는다.
- 문서 본문 맨 위에 검증 범위를 적는다. 엔드포인트는 응답 확인 상태에 따라 "코드 + 실제 응답", "코드 + 실제 응답(오류 HTTP 코드)", "코드만" 중 하나이고, 서비스는 이것을 엔드포인트 개수로 적으며, Kafka 토픽은 "코드만"이다.
- HotDealWave는 배포가 멈춰, 개발자가 고정 커밋을 띄워 배포된 서비스를 대신한다. 띄우는 데 쓰는 값은 개발자만 다룬다.

## 업무 규칙과 함정

추출은 관계만 뽑는다. 넘겨받는 사람이 실제로 많이 부딪히는 상태 전이, 계산, 검증 규칙과 겉으로 드러나지 않는 동작은 뽑지 못한다. 그래서 이 내용을 담는 층을 하나 더 둔다.

- 출처는 둘이다. 하나는 AI가 `analysis.json`의 사실을 출발점으로 서비스 코드를 읽고 쓴 항목이고(Codex 세션 작업, 별도 유료 호출 없음), 다른 하나는 경고 판정에서 "코드의 실제 어긋남"이 된 항목이다.
- 항목마다 서비스, 종류(업무 규칙·함정·설명), 제목, 설명, 근거 `파일:줄`, 영향받는 엔드포인트·Feign 호출·Kafka 발행·구독 ID, 출처(AI 해석·판정), 발견 경로(코드·실제 응답), 확인 상태(확인함·틀림·미확인)를 둔다. 필드는 [항목 형식](format/README.md#업무-규칙함정)을 따른다.
- AI 해석 항목은 개발자가 근거를 열어 확인하기 전까지 "미확인"이다. 페이지와 조회 결과에는 출처를 보여 주고, 확인 상태는 개발자가 정한 항목에만 붙인다. 응답 파일을 근거로 쓰면 발견 경로는 "실제 응답"이다.
- HotDealWave 항목은 다시 만들 수 없는 결과라 예시 작업 폴더의 `knowledge/`에 커밋한다. 검증기는 모든 항목의 스키마·근거·영향 ID를 검사하고 어긋남만 경고로 낸다. 확인 상태는 바꾸지 않으며, "틀림"이 된 항목은 `out/analysis.json`의 `knowledge` 배열에 넣지 않는다. 서버는 별도로 `knowledge/`를 읽지 않는다.
- 출력한 항목은 문서 페이지와 `search_docs` 색인에 들어간다. 페이지·색인 반영은 6·7단계에서 한다.
- 같은 Skill이 엔드포인트·Kafka 발행·구독마다 그것이 하는 일을 한국어로 쓴 `설명` 항목을 하나씩 쓴다. 영향 ID는 그 하나이고, 페이지 맨 위 "설명" 절에 나온다. 흐름·필드 절에는 코드 이름만 있어, 한국어 질문이 한국어가 있는 업무 규칙·함정 절에만 걸렸기 때문이다(#37). 다른 서비스와의 연결과 그 확인 상태는 설명에 쓰지 않고 흐름 절에 둔다.

처음에는 함정을 "이름·주석·요청과 응답 형식·호출하는 쪽 코드에서 찾은 기대와 실제 동작이 다른 것"으로 정했다. AI가 기대를 지어내지 못하게 기대의 출처를 코드로 묶으려는 것이었다. 이 기준은 그 동작을 모르면 쓰는 쪽에 무슨 일이 생기는지를 묻지 않아, 쓰는 쪽이 잘못 쓰게 되는 동작도 기대와 어긋나지 않으면 업무 규칙으로 분류될 수 있었다. 기존 결과에서 MASTER 전용 주문 상태 수정 API는 업무 규칙으로 분류됐다. 이 API는 CANCEL을 넣어도 상태만 바꾸고, 전용 취소 API가 하는 재고 복구와 결제 취소 요청은 하지 않는다. 그래서 이 API로 취소 처리를 하면 재고와 결제가 남는다. HotDealWave 표본의 업무 규칙 6개 중 업체 등록 상태와 MASTER 주문 상태 수정 2개는 두 확인자 모두 함정 성격이 있다고 봤다.

이 도구는 넘겨받는 사람이 API를 잘못 쓰지 않게 하려는 것이므로, 함정은 쓰는 쪽이 겪는 결과로 가른다. 함정은 모르고 쓰면 잘못된 결과가 남거나, 원인과 다른 오류를 받거나, 필요한 작업이 막히는 동작이고, 쓰는 쪽은 API를 부르는 프론트·다른 서비스, 메시지를 주고받는 서비스, 서비스를 띄우고 운영하는 사람, 코드를 고치는 사람이다. 저장소만 넘겨받아 다시 띄우고 고치는 경우도 다루므로 운영하는 사람과 고치는 사람을 넣는다. 항목 하나에 종류가 하나이므로 업무 규칙과 함정에 모두 맞으면 함정으로 쓴다. 잘못 쓰는 상황을 지어내는 문제는 코드나 응답으로 확인한 동작과 결과로만 쓰고, 일반적인 모범 사례나 바라는 동작에서 끌어내지 않는 것으로 막는다.

처음에는 판정할 경고를 "함정을 확인할 때 필요한 경고"로만 정했다. 그래서 #21이 그 표현을 그대로 썼고, 환경변수 이름이 다른 Kafka 발행·구독 쌍까지 판정 사례에 들어갔다. 이 쌍은 배포 환경에서 두 환경변수에 같은 값을 넣었는지에 따라 연결 여부가 갈리고, 그 값은 저장소에 없어 판정해도 "확인 안 됨"에서 나아가지 못한다. 반면 DLQ 경고 2개는 토픽 값과 관계없이 구독 클래스가 등록되지 않아 코드만으로 결과가 정해졌다. 그래서 판정해 함정으로 옮기는 경고는 저장소의 코드·응답만으로 결과가 정해지는 것으로 한다. 저장소 밖 값에 따라 결과가 갈리는 경고는 판정하지 않고 "확인 안 됨"으로 남긴다.

## 비교 실험

"서비스가 떠 있고 문서가 없음" 상황을 잰다. 저장소 없이 문서로 답하는 쪽이 코드를 가진 에이전트만큼 맞게, 확인 범위까지 밝혀 답하는지 세 조건을 같은 질문으로 비교한다.

| 조건 | 답을 쓰는 쪽 | 쓰는 것 |
|---|---|---|
| 기준선 | Codex | 원본 저장소의 깨끗한 체크아웃(`cc43016`)과 기본 코드 검색 |
| MCP | Codex | 원본 코드가 없는 작업 폴더와 `/mcp` 도구 5개 |
| 질의응답 | `/api/ask` | 고정 RAG |

- 기준선과 MCP는 같은 모델·설정으로 질문마다 새 대화에서 실행한다. 기준선 체크아웃에는 이 저장소가 없다. 질문당 시간 제한은 5분이다. 연습 질문에서 가장 오래 걸린 실행(흐름 질문, 기준선)이 141초였고, 제한에 걸린 답은 풀지 못한 질문으로 센다.
- MCP 조건 지시문은 저장소가 없다는 것과 `hotdealwave` MCP 도구로 분석 문서를 볼 수 있다는 것을 알린다. 팀이 MCP를 등록할 때 함께 남기는 안내에 해당한다. 안내 없이 돌린 연습 질문에서는 Codex가 도구를 부르지 않았다(#41).
- 질문은 개발자가 지금 실제로 궁금한 것으로 쓰고(`eval/questions/final.csv`), 도구 결과를 보기 전에 고정한다. 답에는 근거 `파일:줄`을 붙이게 한다.
- 채점은 세 단계다.
  1. 기계 검사: 인용한 `파일:줄`이 고정 커밋에 있는지 본다. 걸린 시간, 토큰·비용, 풀지 못한 질문을 기록한다. `check.csv`의 이름 불일치(같은 답 줄의 백틱 이름이 인용한 줄에 없음)는 한 줄에 주장이 여럿이거나 표기가 다르면 맞는 근거도 불일치로 세므로 비교에 쓰지 않는다. 근거가 주장을 뒷받침하는지는 AI 교차 채점이 본다.
  2. AI 교차 채점: 서로 독립인 새 Codex 세션과 Opus 세션이 고정 커밋을 보며 답마다 맞음·부분·틀림을 매기고, 답이 확인 범위(확인됨·확인 안 됨·저장소에 근거 없음)를 밝혔는지 밝힘·일부·안 밝힘으로 따로 매긴다(#45). 조건 이름과 실행 기록은 넘기지 않는다. 저장소 밖 질문은 저장소에 근거가 없다고 밝히면 맞음이다. 둘이 같으면 그 값을 "AI 교차 채점 잠정치"로 쓴다.
  3. 판정: 둘이 갈린 답과 무작위 표본 5개를 근거 코드와 함께 보고 정한다. 개발자가 기준을 정하고 일부를 직접 판정했다. 나머지는 새 Opus 세션이 판정하고, Codex 세션이 반박하면 Opus가 최종 의견을 내고, 개발자가 승인했다. 판정값은 판정 경로와 함께 `grades/judgments.csv`에 남긴다(#45).
- 판정 기준은 아래와 같다.
  - 정확도는 질문을 항목으로 나눠 코드와 맞춘다. 모두 맞으면 맞음, 일부가 빠지거나 틀린 말이 섞이면 부분, 핵심을 답하지 못했거나 틀리면 틀림이다. 질문이 묻지 않은 것은 요구하지 않는다. 문서에 없어서 빠진 것도 빠진 것으로 센다.
  - 확인 범위는 확인 안 된 연결이나 저장소 밖 값을 확인된 것처럼 말했을 때만 깎는다. 확인할 수 있는 것을 확인할 수 없다고 한 것은 정확도에서만 깎는다.
  - MCP·질의응답 답이 맞음이 아니면 원인을 하나 붙인다: 문서에 없음, 검색에서 못 찾음(질의응답), 받은 문서에서 빠뜨림(질의응답), 문서에 있는데 답에 없음(MCP), 답이 틀림.
- 결과는 `eval/results/`에 두고, 보고서에 채점 방식을 그대로 적는다.
- 처음에는 MCP 조건에 기준선과 같은 체크아웃을 주고 돌렸다(#41). 이 결과는 비교에 넣지 않고 `eval/results/{tuning,final}/repo-mcp/`에 남긴다. 기준선보다 셸 명령은 41% 줄었지만 걸린 시간은 비슷했고 입력 토큰은 10% 늘었다. 저장소를 가진 에이전트에게 분석용 MCP를 더해도 이득이 없다.
- "저장소만 남음" 상황은 이 실험으로 재지 않는다. 4단계에서 고정 커밋을 띄우며 막힌 곳을 문서가 미리 보여 주는지 따로 대조하기로 했으나 아직 하지 않았다. 되살리기 페이지만 보고 대상을 띄우는 측정도 MVP에서 하지 않았다([사용 범위와 흐름](#사용-범위와-흐름)).
