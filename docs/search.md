# 검색과 질의응답

서버가 문서 본문을 어떻게 색인하고 찾는지, 질의응답(`/api/ask`)이 어떻게 답하거나 보류하는지 설명한다. 코드는 `server/src/main/java/io/hotdealwave/server/`의 `Search.java`(색인·검색), `Embeddings.java`(임베딩 저장), `Ask.java`(질의응답), `OpenAiModel.java`(모델 호출)에 있다.

```
[색인]     페이지 본문 -> h2 절 조각 -> 토큰 -> BM25 통계            (서버 메모리, 첫 검색 때)
                                  └-> 임베딩                         (out/embeddings.json, 첫 질문 때)
[검색]     질문 -> 범위 고르기 -> BM25 점수 -> 페이지당 하나 -> 상위 5개   (/api/search, MCP search_docs)
[질의응답] 질문 -> 범위 고르기 -> BM25 순위 + 임베딩 순위 -> RRF -> 상위 8개
                -> 모델 한 번(정해진 형식) -> 인용 검사 -> 답 또는 보류   (/api/ask)
```

## 1. 색인

### 1.1 본문과 조각

- 색인하는 것은 엔드포인트·토픽·서비스 페이지와 배포·모니터링 페이지(`/repository`)의 본문이다. 되살리기 페이지(`/revival`)는 모든 절이 다른 페이지의 반복이라 색인하지 않는다.
- 본문은 화면과 같은 템플릿으로 렌더링한 텍스트다. 근거 링크·접기·상태 색은 브라우저로 보낼 때만 덧씌우므로, 사람·검색·MCP·모델이 읽는 글자가 같다(#39).
- 조각은 본문의 `h2` 절이다. 첫 `h2` 앞부분(설명 등)도 한 조각이다. 엔드포인트 페이지라면 게이트웨이 외부 경로, 요청, 응답, 오류 응답, 나가는 호출과 발행, 부르는 곳이 각각 조각이 된다.
- 조각마다 페이지 주소, 페이지 제목, 절 제목, 페이지 종류(엔드포인트·토픽·서비스·배포·모니터링), 관련 서비스를 붙인다. 종류와 서비스는 2.1의 범위 고르기에 쓴다.

### 1.2 토큰화

코드 이름과 한국어가 섞인 본문을 같은 규칙으로 자른다.

| 대상 | 규칙 | 예 |
|---|---|---|
| 식별자 | 통째로, 그리고 camelCase·snake_case 단위로 | `createOrder` → `createorder`, `create`, `order` |
| 점·하이픈으로 이은 이름 | 통째로, 그 안의 식별자도 통째로 | `order-service.OrderController.createOrder` → 전체, `order`, `service`, `ordercontroller`, `createorder` 등 |
| 한국어 | 두 글자씩 | `쿠폰복구` → `쿠폰`, `폰복`, `복구` |

모두 소문자로 바꾼다. 점 안의 식별자를 따로 넣는 규칙은 `createOrder` 검색에서 서비스 본문이 1위로 나온 것을 보고 더했다(#33).

한국어를 두 글자씩 자르는 것은 조사가 붙으면 띄어쓰기 단위로는 같은 말이 다른 단어가 되기 때문이다("지급한도는"과 "지급한도"). 앞서 만든 RAG 프로젝트(rag-chatbot)의 방식을 옮겨 #33의 확인 조건으로 정했다. 형태소 분석기를 쓰지 않은 이유는 기록되지 않았고, 형태소 분석기와 비교해 잰 적도 없다(7절).

### 1.3 BM25 통계

서버가 처음 검색할 때 모든 조각의 토큰 빈도, 단어마다 그 단어가 나오는 조각 수, 조각의 평균 토큰 수를 메모리에 만든다. 파일로 남기지 않는다. 검증 출력이 바뀌면 서버를 다시 띄운다.

### 1.4 임베딩(질의응답만)

- 조각마다 "페이지 제목 — 절 제목"과 본문을 OpenAI `text-embedding-3-large`로 임베딩한다. 입력 한도를 넘지 않게 3천 자를 넘는 절은 줄 경계에서 여러 조각으로 나눈다.
- 벡터는 검증 출력 옆의 `out/embeddings.json`에 텍스트의 SHA-256 해시를 키로 저장한다. 다음에 띄울 때는 바뀐 절만 다시 만든다. 첫 질문에서 만들므로 그 질문이 조금 느리다.
- 질문은 부를 때마다 한 번 임베딩하고 저장하지 않는다.

### 1.5 쓰는 곳마다 다른 단위

문서가 템플릿으로 만든 페이지라 길이로 자르는 규칙은 따로 없다. 대신 조각을 쓰는 곳마다 단위가 다르다.

| 쓰는 곳 | 단위 | 이유 |
|---|---|---|
| 검색 점수 | `h2` 절 | 처음에는 페이지 단위였고 #33에서 `h2` 절로 바꿨다. 바꾼 이유는 기록되지 않았다 |
| 질의응답 모델 입력 | 엔드포인트·토픽은 페이지 전체, 서비스·배포는 찾은 절 | 절만 넘기면 요청 필드 표나 발행·구독 연결의 상태가 빠졌다(#35, #37) |
| 임베딩 | 절, 3천 자를 넘으면 줄 경계에서 나눔 | 임베딩 입력 한도 |

찾을 때는 절로 좁히고, 답할 때는 그 페이지의 필드와 상태가 빠지지 않게 하는 구조다.

## 2. 검색

### 2.1 범위 고르기

질문에 서비스 이름이나 종류 말이 있으면 그 범위의 조각부터 찾는다.

| 거르는 것 | 알아보는 말 |
|---|---|
| 서비스 | 검증 출력의 서비스 이름(`order-service`)과 서비스 디렉터리의 마지막 이름(`order`) |
| 엔드포인트 | `api`, `엔드포인트` |
| 토픽 | `토픽`, `kafka` |
| 서비스 페이지 | `서비스`, `설정`, `환경변수` |

서비스는 데이터에 있는 이름만 쓰고, 질문의 낱말이 통째로 같을 때만 알아본다. `createOrder` 안의 `order`로는 거르지 않는다. 대상마다 "주문 → order-service" 같은 별칭 표를 손으로 쓰지 않고, 한국어 서비스 말은 BM25에 맡긴다(#33). 처음 보는 저장소에서도 사람 입력 없이 돌아야 하므로, 코드에서 확실히 나오는 서비스 이름과 페이지 종류만 메타데이터로 쓴다. 종류 말은 대상과 상관없는 고정 목록이다.

### 2.2 범위 풀기

결과가 없으면 범위를 하나씩 풀어 다시 찾는다. 서비스와 종류 → 서비스만 → 전체 순서다.

### 2.3 BM25 점수

질문 토큰마다 아래를 더한다. 파라미터는 흔히 쓰는 값(K1=1.2, B=0.75)이다.

```
idf   = ln(1 + (N - df + 0.5) / (df + 0.5))        N: 조각 수, df: 그 토큰이 나오는 조각 수
점수 += idf * tf * (K1 + 1) / (tf + K1 * (1 - B + B * 조각 길이 / 평균 길이))
```

### 2.4 페이지당 하나와 상위 개수

같은 페이지의 조각은 점수가 가장 높은 하나만 남긴다. 긴 페이지가 결과를 독차지하지 않게 하기 위해서다. 검색(`/api/search`, MCP `search_docs`)은 상위 5개, 질의응답은 상위 8개를 낸다. 결과마다 페이지 주소, 절 제목, 점수, 질문어 주변 200자 미리보기가 붙는다.

### 2.5 질의응답의 하이브리드 검색

질의응답만 BM25 순위와 임베딩 순위를 RRF(순위만으로 합치기)로 합친다.

```
임베딩 점수 = 질문 벡터와 조각 벡터의 코사인 유사도(조각을 나눴으면 가장 가까운 조각)
RRF 점수   = Σ 1 / (60 + 순위)                       BM25 순위와 임베딩 순위 각각에서
```

- 더한 이유: 조정용 질문에서 BM25가 표현 차이(예: "HTTP 호출"과 "Feign")로 근거를 놓쳤다(#53의 T04).
- 채택 기준은 결과를 보기 전에 정했다. BM25가 못 찾던 근거를 하나 이상 찾고, BM25가 찾던 근거는 하나도 잃지 않아야 한다. 조정용 질문 T03~T10에서 결과가 갈린 절을 Codex·Opus가 따로 판정하고, 갈린 판정은 개발자가 정했다(#63).
- 상위 5개 RRF는 T03의 근거 2개를 잃어 기준을 채우지 못했다. 상위 8개는 새 근거 13개를 찾고 잃은 근거가 없어 채택했다.
- `/api/search`와 MCP `search_docs`는 BM25 상위 5개 그대로다. MCP는 클라이언트 모델이 검색어를 바꿔 여러 번 찾을 수 있고, 검색 페이지는 키워드 검색이면 충분하다.

## 3. 질의응답

### 3.1 흐름

1. 2.5의 하이브리드 검색으로 상위 8개를 찾는다. 결과가 없으면 보류한다.
2. 결과에 C1~C8 번호를 붙여 모델에 넘긴다. 엔드포인트·토픽 페이지는 찾은 절 대신 본문 전체를 넘긴다. 필드 질문이 설명 절에 걸려도 요청·응답 필드가, 연결 질문이 설명 절에 걸려도 발행·구독 연결의 확인 상태가 함께 가야 하기 때문이다(#35, #37). 나머지는 찾은 절만 넘긴다.
3. 모델을 한 번 부른다(`gpt-6-luna`, 추론 없음, 출력 상한 1500토큰).
4. 인용 검사를 통과하면 답과 인용한 조각을 보여 주고, 아니면 보류한다.

### 3.2 지시문 규칙

모델에 주는 규칙은 `Ask.java`의 `INSTRUCTIONS`에 있다.

- 주어진 조각만 근거로 쓴다. 상식이나 다른 프로젝트 지식으로 보충하지 않는다.
- 조각의 상태 표시를 그대로 옮긴다. "확인 안 됨", "저장소에 근거 없음"인 값은 확정된 것처럼 쓰지 않고 상태와 이유를 밝힌다. 출처가 "AI 해석"인 설명·업무 규칙·함정은 AI 해석이라고 밝힌다.
- 근거는 조각에 적힌 `파일:줄`을 그대로 옮긴다. 조각에 없는 `파일:줄`을 만들지 않는다.
- 조각이 질문의 핵심에 답하면 결론부터 답하고, 확인되지 않는 부분만 확인할 수 없다고 밝힌다.
- 질문이 묻는 것에 대한 답이 조각에 없으면 보류하고 이유를 짧게 쓴다.

### 3.3 정해진 출력 형식

모델은 자유 문장이 아니라 아래 세 칸의 JSON으로 답한다. 서버가 형식을 강제한다.

| 칸 | 뜻 |
|---|---|
| `answer` | 답. 보류할 때는 확인할 수 없는 이유 |
| `citations` | 근거로 쓴 조각 번호(예: `["C1", "C3"]`) |
| `abstain` | 질문이 묻는 것에 대한 답이 조각에 없으면 `true` |

### 3.4 인용 검사와 보류

지시문만으로는 모델이 지키는지 알 수 없어서, 서버가 답을 보여 주기 전에 검사한다.

| 보류 사유 | 언제 |
|---|---|
| 검색 결과 없음 | 범위를 다 풀어도 찾은 조각이 없음 |
| 모델 보류 | 모델이 `abstain: true`로 답함. 모델이 쓴 이유를 함께 보여 줌 |
| 인용 검사: 인용 없음 | 답했는데 인용한 조각이 없음 |
| 인용 검사: 없는 조각 | 넘기지 않은 번호를 인용함 |
| 인용 검사: 인용한 조각에 없는 `파일:줄` | 답에 쓴 `파일:줄`이 인용한 조각의 글자에 없음 |

인용 검사에 걸린 답은 원문을 보여 주지 않는다. 키가 없거나 모델·임베딩 호출이 실패하면 보류가 아니라 오류로 답한다.

### 3.5 한 번에, 질문 하나씩

- 스트리밍하지 않는다. 화면에 먼저 나간 답은 인용 검사를 할 수 없기 때문이다.
- 대화 기록을 넘기지 않는다. "그럼 결제는?" 같은 후속 질문에서 검색이 빗나가고, 채점도 질문 단위로 해야 하기 때문이다.

### 3.6 비용과 시간

질문마다 임베딩 1번과 모델 1번을 부른다. 최종 질문 21개를 다시 돌린 #63에서 시간 중앙값은 4초(최대 14초, 첫 질문에서 바뀐 절의 임베딩을 다시 만듦), 입력 토큰은 모두 합해 973,339, 출력 토큰은 5,404였다. `gpt-6-luna` 입력은 100만 토큰당 0.10달러라 질문 한 번에 1센트 아래다. 키는 `OPENAI_API_KEY` 환경변수에서 읽고, 키가 없어도 서버는 뜨며 질문만 오류로 답한다.

## 4. 설계 결정과 이유

| 결정 | 이유 | 이슈 |
|---|---|---|
| 사람·검색·모델이 같은 본문을 읽음 | 값·상태·근거가 글자로 있어야 어느 쪽에서도 빠지지 않는다 | #28, #39 |
| BM25로 시작하고 임베딩은 필요가 확인될 때만 | BM25가 표현 차이로 근거를 놓치는 경우가 채점에서 확인될 때만 임베딩을 더하기로 했다. 9단계 뒤 조정용 질문에서 확인되어 더했다 | #33, #35, #63 |
| 서비스 별칭 표를 두지 않음 | 대상마다 사람이 손으로 써야 하는 입력이 생긴다 | #33 |
| 한국어는 두 글자씩 | 조사가 붙어도 같은 두 글자가 남는다. 앞서 만든 RAG 프로젝트의 방식을 옮겼다 | #33 |
| 조각 단위를 쓰는 곳마다 다르게 | 1.5절 | #33, #35, #37 |
| 질의응답은 고정 RAG(검색 한 번, 모델 한 번) | 질문당 호출 수가 정해져 비용을 미리 말할 수 있고, 같은 질문으로 다시 재기 쉽다. 여러 단계를 따라가는 질문은 [MCP](mcp.md)가 맡는다 | #35 |
| 엔드포인트·토픽 페이지는 본문 전체를 넘김 | 절만 넘기면 필드 표와 연결 상태가 빠졌다 | #35, #37 |
| 정해진 출력 형식과 인용 검사 | 지시문만으로는 지어낸 근거를 막을 수 없다 | #35 |
| 질의응답만 RRF, 상위 8개 | BM25가 표현 차이로 근거를 놓쳤고, 5개로는 BM25가 찾던 근거가 밀렸다 | #53, #63 |

## 5. 부딪힌 문제와 해결

| 문제 | 해결 | 이슈 |
|---|---|---|
| `createOrder` 검색에서 서비스 본문이 엔드포인트 본문보다 위 | 점으로 이은 이름 안의 식별자도 통째로 토큰에 넣음 | #33 |
| 필드 질문에서 모델이 어노테이션 없는 필드에 앞 줄의 `@NotNull`을 붙임 | 빈 필드를 "어노테이션 없음"으로 씀 | #37 |
| 한국어 질문에서 코드 이름뿐인 흐름 절이 검색되지 않음 | 엔드포인트·메시지마다 한국어 설명 항목(AI 해석)을 페이지 맨 위에 둠 | #37 |
| 연결 질문의 답에 "확인 안 됨"의 이유가 빠짐 | 경고 이유를 식별자 나열에서 문장으로 바꿈 | #37 |
| "HTTP 호출"과 "Feign"처럼 표현이 다르면 BM25가 근거를 놓침 | 질의응답에 임베딩 RRF를 더함 | #53, #63 |
| 질문에 섞인 낱말로 종류가 좁혀져 다른 종류의 근거가 빠짐 | 지시문 수정과 종류 말 수정을 시험했지만 효과가 없거나 다른 질문을 나쁘게 해 채택하지 않음 | #53 |
| 모델이 받은 조각에 없는 `파일:줄`을 인용 | 인용 검사가 보류로 바꿈. 틀린 근거로 답하는 대신 답하지 않음 | #63 |

## 6. 한계

- 문서에 없는 사실은 찾을 수 없다. 9단계에서 질의응답이 맞음이 되지 못한 원인 가운데 가장 많은 것이 이것이었다(추출 범위의 과제).
- 필요한 절이 문서에 있어도 상위 8개에 들지 않으면 보류한다. 최종 질문 21개에서 보류는 9개였고, 답한 12개에는 틀린 답이 없었다([9단계 보고서 9절](reports/eval-hotdealwave.md#9-질의응답-검색을-바꾼-뒤-다시-잰-결과63)).
- 한국어 서비스 말("주문", "결제")로는 범위를 고르지 못한다. 별칭 표를 두지 않은 대가다. 질의응답에서는 임베딩이, MCP에서는 검색어를 바꿔 다시 찾는 클라이언트 모델이 이 공백을 메운다.
- 종류 말은 고정 목록이라 목록에 없는 표현은 범위를 고르지 못한다. 반대로 질문에 섞인 종류 말이 범위를 잘못 좁히기도 한다(#53).
- 한국어 두 글자는 "쿠폰을"의 `폰을`처럼 뜻 없는 조각도 만든다. 이것이 순위를 얼마나 흐리는지 다른 방식과 비교해 잰 적이 없다.
- 색인은 서버 메모리에 있어 검증 출력이 바뀌면 서버를 다시 띄워야 한다.
- 질문 하나씩만 받고 대화를 이어가지 않는다.

## 7. 개선할 수 있는 것

| 무엇 | 방법 | 비용 |
|---|---|---|
| 한국어 토큰화 확인 | Lucene의 한국어 형태소 분석기(Nori)와 두 글자를 조정용 질문 T03~T10에 돌려, 근거 절을 몇 개 찾는지 비교한다 | BM25만 바꾸므로 유료 호출 없음 |
