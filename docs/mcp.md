# MCP

서버의 `/mcp`는 문서를 Claude Code·Codex 같은 코딩 에이전트가 도구로 읽게 한다. 저장소를 받지 못했거나 읽지 않는 사람(서비스 API를 쓰는 프론트엔드 개발자, 에이전트)이 자기 에이전트에게 묻는 경로다. 코드는 `server/src/main/java/io/hotdealwave/server/Mcp.java`에 있다.

## 1. 질의응답과 무엇이 다른가

질의응답(`/api/ask`)은 서버가 검색을 한 번 하고 모델을 한 번 부르는 고정 경로다([검색과 질의응답](search.md)). MCP는 서버가 모델을 부르지 않는다. 클라이언트의 모델이 질문을 보고 도구를 고르고, 필요한 만큼 여러 번 부른 뒤 답을 쓴다.

예를 들어 "주문 생성 API를 부르면 어떤 서비스를 호출하고 무엇을 발행하는지, 이어지지 않는 곳은 이유까지"라는 질문이라면, 질의응답은 상위 8개 조각 안에서만 답한다. MCP에서는 모델이 `find_endpoint`로 엔드포인트를 찾고, `trace_flow`로 나가는 호출을 따라가고, 끊긴 발행이 있으면 `find_subscribers`로 그 토픽을 다시 본다.

| | 질의응답(`/api/ask`) | MCP(`/mcp`) |
|---|---|---|
| 쓰는 쪽 | 브라우저의 사람(검색·질문 페이지) | Claude Code·Codex 같은 에이전트 |
| 검색하는 쪽 | 서버가 한 번 | 클라이언트 모델이 필요한 만큼 |
| 서버의 모델 호출 | 질문마다 임베딩 1번, 모델 1번 | 없음 |
| 근거 확인 | 서버의 인용 검사가 답을 막거나 보여 줌 | 도구 결과의 상태·근거를 모델이 옮김 |
| 걸린 시간(9단계 중앙값) | 4초 | 49초 |
| 최종 질문 21개 | 맞음 5·부분 11·틀림 5(답한 12개에는 틀림 0) | 맞음 12·부분 9·틀림 0 |
| 맞는 질문 | 필드·값·설정처럼 한두 절에 있는 사실 | 서비스 사이 흐름처럼 여러 페이지를 이어 봐야 하는 것 |

질의응답의 숫자는 검색을 바꾼 #63 재실행, MCP의 숫자는 9단계 결과다([9단계 보고서](reports/eval-hotdealwave.md)).

## 2. 도구

다섯 도구 모두 서버의 조회 계층을 그대로 감싼다. 결과는 문서 페이지 본문과 같은 텍스트라, 값마다 상태(확인됨·확인 안 됨·저장소에 근거 없음)와 이유, 근거 `파일:줄`이 붙는다.

| 도구 | 인자 | 결과 |
|---|---|---|
| `find_endpoint` | 엔드포인트 ID, "메서드 경로"(`POST /api/v1/orders`), 경로 또는 핸들러 이름 | 엔드포인트 본문: 요청·응답 필드, 오류 응답, 나가는 호출, 검증 범위, 업무 규칙·함정 |
| `trace_flow` | 엔드포인트, 메시지 발행 또는 구독 ID | "나가는 호출과 발행"과 "부르는 곳"의 단계. 이어지지 않는 곳은 상태와 이유에서 멈춤 |
| `find_subscribers` | 토픽 환경변수 이름 또는 코드에 적힌 토픽 이름 | 토픽 본문: 발행, 구독, 발행 → 구독 연결 |
| `search_docs` | 찾을 말 | BM25 상위 5개 절의 페이지 주소, 절 제목, 점수, 미리보기 |
| `get_page` | 페이지 주소(`/endpoints/ID`, `/topics/이름`, `/services/이름`, `/repository`, `/revival`) | 본문 전체 |

- 결과 머리에는 그 결과에 나오는 배열마다 "확인됨의 뜻"이 붙는다. 예를 들어 HTTP 호출의 확인됨은 "종류에 맞는 호출 선언·HTTP 메서드·경로를 확인했고, 내부 대상은 같은 서비스 이름·HTTP 메서드·경로의 엔드포인트 하나와 대조했다"는 뜻이다.
- `trace_flow`가 지나는 서비스에 도구가 다루지 않는 방식(`unsupported`, 예: 회로 차단기 fallback)이 있으면 그 위치를 밝히고 "이 흐름에는 그 호출이 빠져 있을 수 있다"고 덧붙인다.
- 찾지 못하면 "찾지 못함: 인자"를 오류 결과로 낸다. 9단계에서 MCP 조건의 결과 없음은 26번이었다.
- 서버 지시문은 분석 대상과 고정 커밋, 값마다 상태와 근거가 붙는다는 것, 답할 때 확인되지 않은 값은 상태와 이유를 함께 밝히라는 것을 알린다.

## 3. 전송과 등록

- Streamable HTTP 한 가지이고, 요청마다 독립인 무상태 방식이라 세션을 두지 않는다. 도구는 모두 읽기만 한다.
- 표준 입출력(stdio) 방식은 두지 않는다. Claude Code와 Codex 모두 HTTP 방식 MCP를 등록할 수 있다.
- 서버를 띄운 채 등록한다.

```bash
claude mcp add --transport http handover http://localhost:8080/mcp
```

```bash
codex mcp add handover --url http://localhost:8080/mcp
```

원격에 올리는 경우 `/mcp`는 공개 저장소를 분석한 읽기 전용 데이터라 인증 없이 연다([결정 기록 "배포"](decisions.md#배포)).

## 4. 설계 결정과 이유

| 결정 | 이유 | 기록 |
|---|---|---|
| MCP는 저장소 없이 API를 쓰는 쪽을 위한 창구로 둔다 | 저장소를 가진 사람과 에이전트는 코드를 직접 읽을 수 있다. 저장소와 MCP를 함께 줬을 때 이득이 없었다(6절) | [문제 상황](decisions.md#문제-상황), #41 |
| 도구는 조회 계층을 그대로 감싸고, 결과는 페이지 본문과 같은 텍스트다 | 사람·검색·모델이 같은 본문을 읽어야 값·상태·근거가 어느 쪽에서도 빠지지 않는다 | #28, #39 |
| 결과 머리에 배열마다 "확인됨의 뜻"을 붙인다 | 배열마다 확인한 범위가 다르다. 예를 들어 핸들러 호출 사슬은 출발·도착 줄만 본다 | [검증](decisions.md#검증), #60 |
| 흐름이 지나는 서비스에 `unsupported`가 있으면 밝힌다 | 그 흐름이 완전한지 알 수 있어야 한다 | [추출 방식](decisions.md#추출-방식) |
| `search_docs`는 BM25 상위 5개 그대로 둔다 | 클라이언트 모델이 검색어를 바꿔 여러 번 찾을 수 있다 | [검색](decisions.md#검색) |
| 되살리기 페이지는 `get_page`로만 읽는다 | 모든 절이 다른 페이지의 반복이라 검색 색인에 넣지 않는다 | #68 |
| Streamable HTTP만 두고 표준 입출력 방식은 두지 않는다 | Spring Boot에 바로 붙고, Claude Code·Codex 모두 HTTP 방식 MCP를 등록할 수 있다 | [언어와 라이브러리](decisions.md#언어와-라이브러리) |
| 원격 `/mcp`는 인증 없이 연다 | 공개 저장소를 분석한 읽기 전용 데이터다 | [배포](decisions.md#배포) |

## 5. 써 본 결과

### 클라이언트 확인(#33)

같은 질문 하나("주문 생성 API를 부르면 어떤 서비스를 호출하고 Kafka로 무엇을 발행하는지, 이어지지 않는 곳은 이유까지")로 두 클라이언트를 확인했다. 둘 다 Feign 호출과 `requestProduct` 발행을 `파일:줄`과 함께 답했고, 확인되지 않은 구독 연결을 확인된 것으로 바꾸지 않았다. Codex는 Feign 호출을 4곳 중 3곳만 들었다. 자세한 내용은 [서버 보고서 3절](reports/server-hotdealwave.md#3-7단계-검색과-mcp)에 있다.

### 비교 실험(9단계)

저장소 없이 MCP만 쓴 Codex를, 저장소를 가진 Codex와 같은 질문 21개로 비교했다.

| | 저장소 + Codex | MCP + Codex(저장소 없음) |
|---|---|---|
| 맞음·부분·틀림 | 21·0·0 | 12·9·0 |
| 확인 안 된 것을 확인된 것처럼 말한 답 | 1 | 0 |
| 걸린 시간(중앙값) | 71초 | 49초 |
| 쓴 것 | 셸 명령 182 | 셸 명령 0, 도구 호출 241 |

- 도구 호출은 `search_docs` 139, `get_page` 84, `trace_flow` 8, `find_endpoint` 6, `find_subscribers` 4번이었다. 대부분 검색으로 찾고 본문을 읽었다.
- MCP 답의 파일 인용 580개는 모두 고정 커밋에 있는 줄이었다(검사기가 잘못 읽은 2건 제외).
- 부분 9개 가운데 7개는 문서에 그 내용이 없어서였다. 오류 응답 본문, 페이지 직렬화 설정, 배포 워크플로처럼 그때 아직 추출하지 않은 것이었고, 9단계 뒤 추출 범위에 더했다(#47, #49).

## 6. 부딪힌 문제와 해결

| 문제 | 해결 | 이슈 |
|---|---|---|
| MCP를 등록만 하면 Codex가 도구를 부르지 않음 | 클라이언트 지시문에 "이 도구로 분석 문서를 볼 수 있다"는 안내 한 줄 | #41 |
| 답이 경로를 줄여 써서 인용 102개가 고정 커밋에서 찾아지지 않음 | 클라이언트 지시문에 "저장소 루트 기준 경로 그대로"를 더함. 102개 → 2개 | #43 |
| 저장소와 MCP를 함께 주면 저장소만 쓸 때보다 이득이 없음(셸 명령은 41% 줄었지만 시간은 비슷하고 입력 토큰은 10% 늘어남) | MCP가 필요한 쪽을 "저장소 없이 API를 쓰는 사람"으로 정하고, 그 조건으로 다시 잼 | #41, #43 |

앞의 두 줄은 MCP를 쓰는 사람에게도 해당한다. 에이전트가 도구를 쓰지 않으면 도구가 있다는 것을, 근거 경로를 줄여 쓰면 저장소 루트 기준 경로 그대로 쓰라는 것을 지시문에 넣는다.

## 7. 한계

- 문서에 없는 사실은 답할 수 없다. 도구는 추출 결과만 보여 준다([추출 방식](extraction.md#6-영역별-확인-정도)).
- 시간은 질의응답보다 길다(중앙값 49초 대 4초). 대신 여러 페이지를 이어 보는 질문에 강하다.
- 답의 정확도는 클라이언트 모델에 달려 있다. 9단계의 유일한 "답이 틀림"(Q11)은 문서는 맞았는데 모델이 Kafka ID를 메서드 이름으로 옮겨 쓴 경우였다.
- 저장소만 남은 상황(서비스를 다시 띄우는 사람)은 이 실험으로 재지 않았다.
