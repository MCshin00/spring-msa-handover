# 설계 개요

이 도구가 어떤 문제를 다루고, 왜 이렇게 만들었고, 무엇을 찾아냈는지 한 흐름으로 정리한다. 단계별 설명은 [추출 방식](extraction.md), [검색과 질의응답](search.md), [MCP](mcp.md)에 있고, 정한 것의 전체 목록은 [결정 기록](decisions.md)에 있다.

## 1. 다루는 문제

문서도, 인수인계해 줄 사람도 없이 마이크로서비스 프로젝트를 넘겨받는 경우다. 넘겨받는 상황은 둘로 나뉜다.

| | 서비스가 떠 있고 문서가 없음 | 저장소만 남음 |
|---|---|---|
| 쓰는 사람 | 서비스 API를 쓰는 사람과 에이전트. 코드를 갖지 않았거나 읽지 않는다 | 서비스를 다시 띄울 개발자. 저장소를 가졌다 |
| 필요한 것 | API 요청·응답과 서비스 사이 흐름, 각각 어디까지 확인됐는지 | 띄우는 데 필요한 환경변수·외부 자원, 이어지지 않는 연결, 운영 함정 |
| 보는 곳 | 문서 페이지, 질의응답, MCP | 문서 페이지, 되살리기 페이지 |

예시 대상인 HotDealWave는 저장소만 남은 경우다. 서비스가 떠 있는 경우는 고정 커밋을 띄워 시험했다.

## 2. 기존 방법으로 부족한 점

- **Swagger**: 서비스를 띄워야 보이고, HotDealWave에서는 설명도 거의 없었다. 저장소만 남으면 볼 수 없다.
- **저장소를 가진 AI에게 그때그때 묻기**: 9단계 비교 실험에서 저장소를 가진 Codex는 질문 21개를 모두 맞혔다. 그런데 한 답(Q02)은 서로 다른 토픽 환경변수 사이의 연결을 확인된 것처럼 전제했다. 질문마다 저장소를 다시 읽었다(중앙값 71초, 셸 명령 모두 182번).
- **저장소를 받지 못한 사람**: 서비스 API를 쓰는 프론트엔드 개발자나 그 에이전트는 코드를 갖지 않았거나 읽지 않는다. 저장소를 가진 사람에게 매번 물어야 한다.

## 3. 접근

```
대상 저장소 @고정 커밋
  --> AI 세션이 Skill로 한 번 추출: 사실과 근거 파일:줄만 씀
  --> verify: 검증기가 근거 줄과 양쪽 연결을 대조해 상태를 정함
        확인됨 / 확인 안 됨 / 저장소에 근거 없음
  --> serve: 같은 본문을 네 곳이 읽음
        문서 페이지(사람) · 검색 · 질의응답(서버가 모델 한 번) · MCP(클라이언트의 모델)
```

- **한 번 추출해 데이터로 남긴다.** 질문마다 저장소를 다시 읽지 않는다. 저장소가 없는 사람도 같은 결과를 본다.
- **AI는 사실을 쓰고, 상태는 검증기가 정한다.** AI가 그럴듯한 연결을 만들어도 근거 줄로 대조되지 않으면 "확인 안 됨"으로 남는다([추출 방식 2절](extraction.md#2-ai는-사실을-쓰고-상태는-검증기가-정한다)).
- **저장소 밖에만 있는 사실은 없다고 밝힌다.** 환경변수 값, 등록된 시크릿, 콘솔 설정은 "저장소에 근거 없음"이다.
- **AI 해석은 출처를 단다.** 업무 규칙·함정·설명은 AI가 코드를 읽고 쓴 해석이라 "AI 해석"으로 표시하고, 개발자가 확인하기 전까지 미확인이다.
- **사람·검색·모델이 같은 본문을 읽는다.** 값·상태·근거가 글자로 있어서 어느 쪽에서도 빠지지 않는다.
- **사람이 정답표나 별칭 표를 쓰지 않는다.** 넘겨받는 사람도 구조를 모른 채 시작하고, 도구는 처음 보는 저장소에서 사람 입력 없이 돌아야 한다. 그래서 검증은 코드와 대조하고, 검색은 코드에서 나온 이름만 범위 고르기에 쓴다.

단계마다 정한 것과 이유는 [추출 방식 5절](extraction.md#5-설계-결정과-이유), [검색과 질의응답 4절](search.md#4-설계-결정과-이유), [MCP 4절](mcp.md#4-설계-결정과-이유)에 표로 있다.

## 5. 기술 선택

| 부분 | 선택 | 이유 |
|---|---|---|
| 추출 | AI 세션(Claude Code·Codex)과 Skill | 프레임워크가 달라도 지시문으로 따라간다. 사용자의 세션으로 돌아 별도 유료 호출이 없다 |
| 검증 | Java 17 검증기 | 서버와 같은 실행 환경이다. 추출의 확인 상태를 사람 판단 없이 근거 줄로 정한다 |
| 서버 | Spring Boot, Thymeleaf | 검증기와 같은 실행 환경 하나로 빌드·테스트한다. 화면 모양은 중요하지 않다 |
| 명령 | `java -jar handover.jar init / verify / serve` | jar 하나라 OS마다 실행 파일을 따로 두지 않는다 |
| 검색 | BM25, 질의응답만 임베딩 RRF | BM25로 시작하고, 표현 차이로 근거를 놓치는 것이 확인되어 질의응답에 임베딩을 더했다([검색과 질의응답 2.5절](search.md#25-질의응답의-하이브리드-검색)) |
| 질의응답 | 검색 한 번, 모델 한 번, 인용 검사 | 질문당 호출 수가 정해져 비용을 미리 말할 수 있다. 지어낸 근거는 서버가 막는다 |
| MCP | MCP Java SDK, Streamable HTTP | Spring Boot에 바로 붙고, Claude Code·Codex 모두 HTTP 방식을 등록할 수 있다 |

## 6. 도구가 찾아낸 것

**HotDealWave: 확인 안 된 연결 13개**

검증 경고 13개가 모두 이유와 할 일을 달고 첫 화면과 되살리기 페이지에 나온다. 저장소 밖 값 때문에 잇지 못한 것 9개(예: 주문 서비스의 상품 요청 발행은 토픽이 환경변수로 정해지고, 같은 환경변수를 쓰는 구독이 저장소에 없음), 저장소 안에 상대가 없는 것 4개다. 예는 [추출 방식 3절](extraction.md#메시지-연결이-확인되지-않는-경우)에 있다.

**HotDealWave: 관리자 주문 상태 수정의 부수 처리 없음**

`PUT /api/v1/orders/{orderId}/status`는 MASTER가 주문 상태를 요청한 값으로 그대로 바꾼다. 이전 상태 검사, 재고 복구, 결제·쿠폰 호출이 없어, 이 경로로 취소·환불 상태를 지정하면 전용 취소 API와 달리 재고와 결제가 되돌아가지 않는다(`order/.../OrderService.java:250`, `OrderController.java:65`). 업무 규칙 항목(AI 해석, 미확인)이며, 5단계에서 두 AI가 따로 코드와 대조해 둘 다 맞다고 봤다([5단계 보고서](reports/rules-hotdealwave.md)).

**SpartaHub: 두 번째 저장소**

- 업무 규칙 50개, 함정 65개, 설명 56개, 모두 171개를 썼다(AI 해석, 미확인).
- 남은 검증 경고 16개의 원인을 모두 나눴다. 추출 잘못 7개, 실제 코드 문제 3개(부르는 곳 없는 Feign 메서드 2개, 받는 처리기 없는 예외 1개), 도구가 모르는 형태 6개다([10단계 보고서 4.4절](reports/general-msa-spartahub.md#44-경고-16개)).

## 8. 한계

- 문서에 없는 사실은 어느 경로로도 답할 수 없다. 영역별로 어디까지 확인했는지는 [추출 방식 5절](extraction.md#6-영역별-확인-정도)에 있다.
- 검색은 한국어 서비스 말로 범위를 고르지 못하고, 한국어 토큰화(두 글자씩)는 다른 방식과 비교하지 않았다. 약한 점과 개선 방향은 [검색과 질의응답 6·7절](search.md#6-한계)에 있다.
- 실제 저장소로 써 본 것은 두 개다. RestClient·WebClient·HTTP 인터페이스, RabbitMQ·Stream은 대표 테스트로만 확인했다.
- 대상이 바뀐 뒤 변경분만 다시 분석하는 일은 다루지 않는다. 고정 커밋과 다르면 `verify`가 멈춘다.
- 저장소만 남은 상황에서 되살리기 페이지만으로 실제로 띄울 수 있는지는 재지 않았다.
- 남은 과제는 [10단계 보고서 7절](reports/general-msa-spartahub.md#7-남은-과제)에 있다.
