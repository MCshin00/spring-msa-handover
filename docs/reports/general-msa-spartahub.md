# 10단계 보고서: Spring MSA 일반화와 두 번째 대상

HotDealWave에 맞춰 만든 도구를 다른 Spring Boot·Spring Cloud MSA 저장소에도 쓸 수 있게 넓히고, 두 번째 대상 [13th-SpartaHub-Backend](https://github.com/13th-SpartaHub/13th-SpartaHub-Backend)(고정 커밋 `caba61c`)에 처음 쓰는 사람의 순서로 돌려 본 결과다.

## 1. 요약

- 도구를 대상과 떼어 냈다. 사용자는 `init`으로 대상과 커밋을 받고, 작업 폴더에서 AI 세션을 열어 추출을 시키고, `serve`로 결과를 본다. 도구 저장소와 사용자 체크아웃은 바뀌지 않는다.
- 서비스 간 통신 형식을 특정 기술 이름에서 역할로 일반화했다. Spring이 제공하는 HTTP 호출 다섯 방식과 메시지 세 방식을 같은 배열과 `kind`로 담고, 선언 줄 규칙은 한 곳에 모았다.
- SpartaHub 시험에서 도구 결함 네 가지를 찾아 고쳤다. 고친 Skill로 처음부터 다시 추출하자 첫 시도의 경고 52개가 16개로 줄었고, 확인된 내부 호출 대상은 2개에서 20개로 늘었다. 남은 경고 16개는 추출 잘못 7, 실제 코드 3, 도구가 모름 6이다. 서비스 10개를 하위 에이전트로 동시에 추출해 업무 규칙·함정까지 약 47분 걸렸다.
- 결과 파일에 대상 저장소의 비밀값은 들어가지 않았다.
- 질의응답 검색을 BM25와 임베딩의 RRF로 바꿨다. 답한 답에는 틀린 답이 없고, 답한 답의 맞음이 3개에서 5개로 늘었다.
- 저장소만 남았을 때 띄우는 데 필요한 것을 한 페이지에 모은 되살리기 페이지를 더했다.

## 2. 쓰는 흐름

```
java -jar build/handover.jar init --repo <대상> --commit <커밋> --workspace <작업 폴더>
  --> 작업 폴더의 source/(고정 커밋), target.json, AI 세션용 지시 파일
작업 폴더에서 AI 세션: 서비스 → 관계 → 저장소 수준 → (응답 확인) → verify → 업무 규칙·함정 → verify
  --> services/, relations.json, repository.json, knowledge/, out/analysis.json
java -jar build/handover.jar serve
  --> 문서 페이지, 검색·질의응답, MCP, 되살리기 페이지
```

## 3. 일반화 범위

지원 기준은 특정 분석 대상이 아니라 Spring이 제공하는 서비스 간 통신 방식이다.

| 구분 | 다루는 것 | 다루지 않는 것 |
|---|---|---|
| HTTP 호출 | OpenFeign, RestTemplate, RestClient, WebClient, HTTP 인터페이스(`httpClients`·`httpCalls`, `kind`) | gRPC, GraphQL, WebSocket |
| 메시지 | Kafka, RabbitMQ, Spring Cloud Stream(`messageDeclarations`·`messagePublications`·`messageSubscriptions`, 관계 파일 `messageLinks`) | |
| 호출 대상 | 서비스 이름, 코드에 적힌 외부 URL, 설정값(저장소에 근거 없음), 조립한 주소(확인 안 됨) | |
| 그 밖 | | 회로 차단기 fallback, 재시도: `unsupported`로 남고 서비스 페이지와 흐름 결과에 나온다 |

새 방식을 더할 때 고칠 곳은 추출 Skill의 종류별 표와 검증기의 `CommunicationRules` 두 곳이다. 서버의 흐름 추적은 바꾸지 않는다. HotDealWave 예시는 배열 이름과 `kind`만 옮겼고, 상태 수(확인됨 5,079, 확인 안 됨 76, 저장소에 근거 없음 336)와 경고 13개가 그대로다.

## 4. SpartaHub 시험

### 4.1 대상

서비스 10개(게이트웨이, 유레카 서버, 업무 서비스 8개)의 Spring Boot·Spring Cloud MSA다. 서비스 사이는 OpenFeign으로 부르고, 외부 API는 Feign(설정값 주소)과 RestTemplate으로 부른다. 메시지 브로커는 쓰지 않는다. 대부분의 Feign 호출에 Resilience4j 회로 차단기가 붙어 있다.

### 4.2 첫 시도와 고친 결함

도구를 새로 받아 처음 쓰는 사람의 순서(`init` → "추출해 줘" → `verify` → `serve`)로 돌렸다. 첫 `verify`의 경고는 52개였고, 원인을 보니 도구 결함 네 가지가 섞여 있었다. #66에서 고쳤다.

| 결함 | 고친 것 |
|---|---|
| 매핑 어노테이션의 `headers` 등 다른 속성 문자열까지 경로로 읽어, 맞게 추출한 Feign 호출 22개가 "확인 안 됨"이 됨 | 경로는 첫 위치 인자와 `value`·`path`에서만 읽는다 |
| 검증기가 추출의 `external`을 덮어써 외부 호출 3개가 내부 호출로 나옴 | 추출 값을 보존하고, 어긋나면 경고한다 |
| 허용 목록의 빈 `httpMethod`에서 `verify`가 멈춤 | "확인 안 됨"과 경고로 낸다 |
| 지시 파일이 추출을 나눌 수 있다는 문장뿐이라 한 세션이 서비스를 차례로 읽음 | 서비스 수와 함께 "동시에 / 차례로"를 사용자에게 묻는다 |

HotDealWave 테스트가 이 결함을 잡지 못한 것은 규칙과 테스트 기대값을 HotDealWave 코드에서 정했기 때문이다. HotDealWave에는 매핑의 `headers`·`params` 같은 속성도, 설정값 주소의 외부 호출도, 메서드 없는 허용 목록도 없었다. 결함 1·3의 원인은 "고정 커밋에 없는 경우를 위한 처리를 넣지 않는다"는 개발 규칙이 Spring 어노테이션의 정의까지 막은 것이다. 규칙에 "대상이 쓰는 Spring 기능은 고정 커밋에 나오지 않은 속성·형태까지 그 기능의 정의대로 읽는다"를 더했다.

고친 검증기로 같은 추출을 다시 검증하자 경고 35개, 확인된 내부 호출 대상 19개, 외부 호출 3개가 됐다.

### 4.3 고친 Skill로 다시 추출

남은 경고 중 22개는 Feign 매핑을 선언 목록에 넣지 않은 추출에서 나왔다. Skill에 그 규칙을 적은 뒤, 새 작업 폴더에서 지시 파일의 순서대로 처음부터 다시 추출했다. 서비스별 하위 에이전트로 동시에 추출했고, 업무 규칙·함정까지 약 47분 걸렸다. 테스트 서버가 없어 응답 확인은 하지 않았다.

| | 첫 시도 | 결함 수정 후 재검증 | 재추출 |
|---|---|---|---|
| 경고 | 52 | 35 | 16 |
| 선언 목록 경고 | 22 | 22 | 0 |
| 확인된 내부 호출 대상 | 2 | 19 | 20 |
| 외부 호출 | 0 | 3 | 3 |
| 스키마 경고 | 0 | 0 | 0 |
| 업무 규칙·함정·설명 | 없음 | 없음 | 50·65·56 |

관계 파일에는 `calls` 73개, `throws` 196개가 있고 `messageLinks`는 없다(메시지를 쓰지 않음). `unsupported`는 30곳(회로 차단기 28, 재시도 2)이다.

### 4.4 경고 16개

경고마다 근거 줄과 추출 항목을 열어 원인을 나눴다. 메인 세션의 초안과 Codex의 독립 분류를 맞대 보고, 갈린 한 묶음은 형식 스키마를 확인해 정한 뒤 개발자가 확정했다.

| 묶음 | 수 | 코드에서 본 것 | 판정 |
|---|---|---|---|
| 응답 DTO jsonName | 3 | 근거가 `@Getter` 줄이 아닌 한 줄 아래 `@AllArgsConstructor` 줄 | 추출 잘못 |
| 게이트웨이 허용 목록 `httpMethod` | 4 | 경로만 비교하고 메서드는 비교하지 않음. 형식은 정할 수 없는 값을 `null`과 이유로 받는데, 이유는 맞게 쓰고 값을 빈 문자열로 씀 | 추출 잘못 |
| 부르는 곳 없는 Feign 메서드 | 2 | 인터페이스 선언만 있고 부르는 곳이 없음 | 실제 코드 |
| 받는 처리기 없는 예외 | 1 | `NoSuchElementException`을 받는 처리기가 없어 기본 오류 응답으로 나감. 회로 차단기 fallback이 바꿔 던지는 예외도 처리기가 없음 | 실제 코드 |
| 인자 없는 `@PostMapping` 경로 | 2 | `@FeignClient`에 `path`가 없고 매핑에도 경로가 없어, 빈 경로를 보여 줄 줄이 없음 | 도구가 모름 |
| 조립한 오류 메시지 | 1 | 필드 이름과 enum 메시지를 이어 붙임. 형식의 메시지 출처에 "조립"이 없음 | 도구가 모름 |
| 이미지만 쓰는 컨테이너 | 2 | compose가 `image`만 쓰고 Dockerfile이 없어 빌드 명령·EXPOSE가 원래 없음. 형식에 "해당 없음"이 없음 | 도구가 모름 |
| 서비스 사이 항목 중복 | 1 | 게이트웨이 함정과 사용자 서비스 설명 항목의 영향 ID가 같음. 종류와 내용이 달라 중복이 아님 | 도구가 모름 |

합계는 추출 잘못 7, 실제 코드 3, 도구가 모름 6이다. 추출 잘못 7개는 모두 표기·근거 줄 선택의 잘못이고, 검증기가 그 값을 "확인됨"으로 내지 않고 경고로 잡았다.

### 4.5 처음 쓰는 사람의 순서에서 본 것

- `init`이 마지막에 "추출해 줘"라고 하라고 안내한다. 첫 시도의 세션은 이 말을 받고 `verify`에서 멈춰, 업무 규칙·함정 단계를 하지 않았다. 재추출은 "지시 파일대로 끝까지"로 시켰다.
- 세션이 관계 파일을 쓰기 전에 중간 점검으로 `verify`를 부르자, 안내 없이 오류 스택만 찍혔다. 지시 순서 밖이지만 AI 세션이 할 만한 행동이다.
- 헤더 파라미터의 `name`을 서비스마다 Java 변수명과 헤더 이름으로 다르게 썼다. 형식 문서에 이 경우의 규칙이 없다.
- 게이트웨이 허용 목록이 메서드를 비교하지 않아 모든 엔드포인트의 토큰 필요 여부가 "확인 안 됨"이다. 형식 규칙대로 확정하지 않은 결과다.
- 업무 규칙·함정 정리에서 서로 전제가 다른 항목 두 쌍(fallback 적용 여부, 잘못된 정렬 값의 응답 상태)을 그대로 남겼다. 새 주장을 더하지 않는 Skill 규칙 때문이다. 모두 AI 해석이라 개발자 확인 전이다.

## 5. 질의응답 검색(#63)

질의응답의 검색을 BM25와 임베딩(`text-embedding-3-large`)의 RRF로 바꾸고, 모델에 넘기는 조각을 상위 8개로 늘렸다. 조정용 질문에서 BM25와 결과가 갈린 절을 두 모델이 따로 판정하고 갈린 판정은 개발자가 정했다. 5칸 RRF는 근거 2개를 잃어 채택하지 않았고, 8칸 RRF는 새 근거 13개를 찾고 잃은 근거가 없어 채택했다.

| 질의응답 | 답함 | 보류 | 합계 |
|---|---|---|---|
| 9단계(BM25 상위 5개) | 13: 맞음 3·부분 10·틀림 0 | 8: 맞음 3·부분 1·답하지 못함 4 | 맞음 6·부분 11·답하지 못함 4 |
| #63(RRF 상위 8개) | 12: 맞음 5·부분 7·틀림 0 | 9: 부분 4·답하지 못함 5 | 맞음 5·부분 11·답하지 못함 5 |

두 번 모두 답한 답에는 틀린 답이 없고(표의 "틀림 0"), 답하지 못함은 근거가 부족해 보류한 답이다. 채점 값으로는 틀림이다. 남은 원인은 문서에 없는 사실(서비스 종료·준비 상태처럼 아직 추출하지 않은 것), 검색이 못 찾은 절, 조각 밖 인용을 막는 인용 검사다. 자세한 결과는 [9단계 보고서 9절](eval-hotdealwave.md#9-질의응답-검색을-바꾼-뒤-다시-잰-결과63)에 있다.

## 6. 되살리기 페이지(#68)

`/revival`은 외부 자원, 채워야 할 환경변수(이름별로 묶음), 저장소 밖 비밀값, 컨테이너, 띄울 때 확인할 연결(경고 이유별 할 일), 운영 함정, 도구가 다루지 않은 위치를 검증 출력에서 모은다. 새로 뽑지 않으므로 검색·질의응답 색인에서는 빼고 MCP `get_page`로 읽는다.

SpartaHub 결과로 띄우면 이렇게 나온다.

- 외부 자원 9개(DB 8, Redis 1)
- 채워야 할 환경변수 13개. 예: `JWT_SECRET_KEY`(4개 서비스), `LOCAL_DB_ENDPOINT`(6개 서비스, dev 프로필), `GEMINI_API_KEY`
- 저장소 밖 비밀값: 없음(배포 파이프라인이 없음)
- 컨테이너: redis-stack 하나(compose 파일이 하나뿐)
- 띄울 때 확인할 연결: 4절의 경고 16개를 이유별로
- 운영 함정 65개, 도구가 다루지 않은 위치 30곳

이 페이지만 보고 대상을 실제로 띄워 막힌 곳을 기록하는 측정은 하지 않았다. DB·외부 API 키를 직접 준비해야 해서 MVP 기간에는 무리였다. 외부 API(Gemini, Slack, 카카오)는 HTTP 호출에는 외부 호출로 나오지만 외부 자원 절에는 나오지 않는다.

## 7. 남은 과제

- 4.4절의 "도구가 모름"과 4.5절의 관찰을 고칠지: 빈 경로, 메서드를 비교하지 않는 허용 목록, 조립한 메시지, 이미지만 쓰는 컨테이너, 설명 항목까지 비교하는 중복 검사, `init` 안내 문구, 관계 파일이 없을 때의 `verify` 안내, 헤더 파라미터 이름 규칙
- 되살리기 페이지에 외부 API를 넣을지, 실제로 띄우는 측정
- 서비스 종료·준비 상태처럼 질의응답이 놓친 사실의 추출
