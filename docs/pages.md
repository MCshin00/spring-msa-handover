# 문서 페이지와 되살리기 페이지

서버가 검증 출력(`out/analysis.json`)으로 만드는 페이지를 설명한다. 사람이 브라우저로 읽는 창구이고, 같은 본문을 검색·질의응답·MCP가 읽는다. 코드는 `server/src/main/java/io/hotdealwave/server/`의 `Pages.java`(본문), `View.java`(값·상태·근거 표기), `Decor.java`(꾸미기), `Legend.java`(확인됨의 뜻)와 `server/src/main/resources/templates/`에 있다.

```
out/analysis.json
  --> Pages + 템플릿: 본문 텍스트 (값, 상태, 이유, 근거 파일:줄)
        +--> 검색 색인, 질의응답 모델 입력, MCP 결과      글자 그대로
        +--> Decor: 브라우저로 보낼 때만 덧씌움            근거 접기·링크, 상태 색, 흐름 상자
```

## 1. 페이지 종류

| 페이지 | 주소 | 담는 것 |
|---|---|---|
| 첫 화면 | `/` | 서비스·엔드포인트·실제 응답 기록·메시지 목적지·확인 안 된 연결의 수, 서비스 카드, 메시지 목적지 표, 확인 안 된 연결 목록 |
| 엔드포인트 | `/endpoints/<ID>` | 검증 범위, 설명, 게이트웨이 외부 경로와 토큰 필요 여부, 요청·응답 필드, 오류 응답, 나가는 호출과 발행, 부르는 곳, 업무 규칙·함정 |
| 토픽 | `/topics/<이름>` | 발행, 구독, 발행 → 구독 연결. 주소는 토픽 환경변수 이름이고, 코드에 문자열로 적힌 토픽은 그 문자열이다 |
| 서비스 | `/services/<이름>` | 엔드포인트 목록, HTTP 호출, 메시지 발행·구독, 환경변수, 외부 자원, 페이지 직렬화, 오류 코드, 예외 처리기, Gateway 거부 응답, 도구가 다루지 않는 방식 |
| 배포·모니터링 | `/repository` | 배포 파이프라인, 컨테이너, 메트릭 수집, 로그 전송, 모니터링 도구 설정과 실행 정의 |
| 되살리기 | `/revival` | 띄우는 데 필요한 것을 다른 페이지에서 모은 것(4절) |
| 응답 원문 | `/responses/<파일>` | 응답 확인 단계에서 저장한 응답 JSON. 근거가 응답이면 그 줄로 링크한다 |

서버는 검증 출력 하나만 읽는다. 대상 저장소의 파일을 열지 않으므로, 대상 코드가 없는 곳에 결과만 올려 띄울 수 있다.

## 2. 본문에 값을 적는 방식

- **값마다 상태와 근거가 붙는다.** 근거는 `파일:줄`이고, 값이 확인되지 않았으면 값 자리에 상태("확인 안 됨", "저장소에 근거 없음")와 이유가 나온다.
- **확인됨은 따로 표시하지 않는다.** 상태가 붙지 않은 값이 확인됨이다. 페이지마다 "확인됨의 뜻"을 펼치면 그 페이지에 나오는 배열마다 무엇을 확인했는지가 한 줄씩 나온다. 예를 들어 핸들러의 호출 사슬은 "출발 항목의 첫 줄과 도착 줄만 확인했다. 중간 줄이 실제로 이어지는지는 보지 않는다"이다.
- **엔드포인트 맨 위에 검증 범위를 적는다.** 응답 확인 결과에 따라 "코드 + 실제 응답", "코드 + 실제 응답(오류 HTTP 코드)", "코드만" 중 하나다. 코드에서 읽은 필드와 관찰한 응답이 다르면 "코드와 실제 응답" 줄에 나란히 나온다. 서비스 페이지는 이것을 엔드포인트 개수로 적고, 토픽은 "코드만"이다.
- **흐름은 이어지지 않는 곳에서 멈춘다.** "나가는 호출과 발행"은 핸들러의 호출, 호출 대상 엔드포인트, 발행과 구독의 연결, 구독 핸들러의 호출 순으로 따라간다. 이어지지 않는 발행에서는 상태와 경고 이유를 붙이고 멈춘다.
- **AI 해석은 출처를 단다.** 설명은 페이지 맨 위, 업무 규칙·함정은 맨 아래에 모으고 함정을 먼저 보인다. 항목마다 종류와 출처("AI 해석", "판정")가 붙고, 확인 상태는 개발자가 정한 항목에만 붙는다.

## 3. 첫 화면의 확인 안 된 연결

검증 경고를 이유 코드별로 묶고, 묶음마다 읽는 사람이 할 일을 한 줄로 붙인다. 같은 묶음이 되살리기 페이지의 "띄울 때 확인할 연결"에도 나온다.

| 이유 코드 | 제목 | 할 일 |
|---|---|---|
| `outside-value` | 저장소 밖 값 | 값이 배포 환경의 환경변수에서 정해진다. 배포 환경에서 양쪽 값을 확인한다 |
| `unlinked` | 저장소 안에서 잇지 못함 | 저장소 안에 상대(구독·발행, 부르는 곳, 외부 경로, 받는 처리기)가 없다. 근거 줄을 보고 끊긴 연결인지, 저장소 밖에서 쓰는지 확인한다 |
| `target-mismatch` | 연결 대상이 어긋남 | 추출 오류이거나 코드의 호출과 대상이 실제로 어긋난 것이다. 양쪽 근거 줄을 열어 본다 |
| `extraction-mismatch` | 근거 줄과 맞지 않음 | 근거 줄을 열어 코드의 값을 직접 본다 |
| `inventory-mismatch` | 선언 목록과 다름 | 그 위치의 선언을 직접 본다 |

이 밖에 근거 파일·줄이 없는 경우, 도구가 읽지 않는 파일 종류, 형식에 맞지 않는 추출 결과, 업무 규칙·함정의 대상 없음과 중복까지 코드는 모두 11개다(`verifier/.../Checks.java`).

HotDealWave의 경고 13개는 "저장소 밖 값" 9개와 "저장소 안에서 잇지 못함" 4개로 나뉜다. SpartaHub의 16개도 같은 화면에 이유별로 나온다.

## 4. 되살리기 페이지

저장소만 남았을 때 서비스를 다시 띄울 사람이 보는 페이지다. 새로 뽑는 것은 없고, 검증 출력에 이미 있는 것을 띄우는 순서로 모은다.

| 절 | 모으는 것 | 원래 있는 곳 |
|---|---|---|
| 외부 자원 | DB·Redis·브로커 같은 자원과 그것을 쓰는 설정·코드 줄 수, 외부 HTTP API(서비스·주소·경로) | 서비스 페이지 |
| 채워야 할 환경변수 | 값이 저장소에서 확인되지 않은 환경변수. 이름마다 읽는 서비스·프로필·설정 위치를 묶는다 | 서비스 페이지 |
| 저장소 밖 비밀값 | 배포 파이프라인이 참조하는 비밀값의 이름. 값은 "저장소에 근거 없음"이다 | 배포·모니터링 페이지 |
| 컨테이너 | 서비스별 이미지, 기반 이미지, 여는 포트 | 배포·모니터링 페이지 |
| 띄울 때 확인할 연결 | 검증 경고를 이유별로 묶은 것과 할 일 | 첫 화면 |
| 운영 함정 | 종류가 함정인 항목 전부 | 엔드포인트·서비스 페이지 |
| 도구가 다루지 않은 위치 | `unsupported`로 남은 위치와 방식 | 서비스 페이지 |

HotDealWave에서는 외부 자원이 15개이고, 채워야 할 환경변수의 값은 모두 "저장소에 근거 없음"이다. SpartaHub 결과로 띄우면 외부 자원 9개(DB 8, Redis 1), 채워야 할 환경변수 13개(예: `JWT_SECRET_KEY`는 4개 서비스), 저장소 밖 비밀값 없음(배포 파이프라인이 없음), 컨테이너 1개, 확인할 연결 16개, 운영 함정 65개, 도구가 다루지 않은 위치 30곳이 나온다([10단계 보고서 6절](reports/general-msa-spartahub.md#6-되살리기-페이지68)).

## 5. 꾸미기

본문은 텍스트로 만들고, 브라우저로 보낼 때만 아래를 덧씌운다.

- 근거 `파일:줄`은 "근거 N개"로 접어 두고, 펼치면 고정 커밋의 GitHub 원본 줄이나 응답 원문 페이지의 그 줄로 가는 링크가 나온다. 근거를 확인하려고 파일을 찾아 열 필요가 없다.
- 확인되지 않은 값의 이유도 접어 둔다.
- 줄과 항목을 상태(확인 안 됨, 저장소에 근거 없음, AI 해석)별 색으로 가른다.
- 흐름 단계는 상자와 화살표로 잇는다. 그림 라이브러리 없이 본문의 단계 줄을 CSS로 잇는다.

검색·MCP·모델이 읽는 본문 글자는 꾸미기 전과 같다. 꾸미기를 넣을 때 전후 724개 절의 텍스트를 비교해 차이가 없는 것을 확인했다(#39).

## 6. 설계 결정과 이유

| 결정 | 이유 | 기록 |
|---|---|---|
| 본문을 처음부터 텍스트로 만든다 | 같은 본문을 사람·검색·모델이 읽는다. 값·상태·근거가 글자로 있어야 어느 쪽에서도 빠지지 않는다 | [서버 보고서 2절](reports/server-hotdealwave.md#2-6단계-조회-계층과-본문), #28 |
| 꾸미기는 브라우저로 보낼 때만 덧씌운다 | 화면을 고쳐도 검색·MCP·모델이 읽는 글자가 바뀌지 않게 한다 | [검색](decisions.md#검색), #39 |
| 서버는 검증 출력 하나만 읽는다 | 대상 코드가 없는 곳에 결과만 올려 띄울 수 있어야 한다 | [사용 범위와 흐름](decisions.md#사용-범위와-흐름) |
| 대상 이름·고정 커밋·근거 링크 주소를 분석 데이터에서 읽는다 | 서버가 대상마다 고쳐지지 않게 한다 | [추출 방식](decisions.md#추출-방식), #55 |
| 확인되지 않은 값에만 상태와 접은 이유를 붙이고, 확인됨은 표시하지 않는다 | 처음 쓰는 사람이 결과만 보고 무엇이 확인됐고, 확인 안 된 것은 왜이며, 무엇을 하면 되는지 알 수 있어야 한다. 그 전에는 확인됨에도 상태 표시가 붙었다 | [검증](decisions.md#검증), #60 |
| 배열마다 "확인됨의 뜻"을 페이지에 둔다 | 확인됨이 무엇을 확인했는지가 어디에도 없었고, 배열마다 확인한 범위가 다르다. 호출 사슬은 출발·도착 줄만 본다 | [검증](decisions.md#검증), #60 |
| 엔드포인트 맨 위에 검증 범위를 적는다 | 확인 상태만으로는 응답으로 확인한 사실과 코드로만 확인한 사실이 구분되지 않는다 | [응답 검증](decisions.md#배포된-서비스-응답-검증), [4단계 보고서 7절](reports/probe-hotdealwave.md#7-한계) |
| 경고를 이유 코드로 묶고 코드마다 할 일을 붙인다 | 검사 이름만으로는 원인이 갈리지 않는다. HotDealWave의 메시지 연결 경고 11개 가운데 DLQ 2개는 저장소 밖 값과 상관없이 끊긴 연결이었다 | [검증](decisions.md#검증), #60 |
| 경고를 읽는 사람에게 판정하게 하지 않는다 | 경고는 "확인 안 됨"과 이유, 할 일로 나온다. 다시 추출하는 것은 도구를 고치는 사람의 일이다 | [검증](decisions.md#검증) |
| 되살리기 페이지는 새로 뽑지 않고 있는 데이터를 모은다 | 띄우는 데 필요한 것이 서비스 페이지(외부 자원·환경변수), 배포·모니터링 페이지(컨테이너·비밀값), 첫 화면(확인 안 된 연결), 엔드포인트 페이지(함정)에 흩어져 있었다 | [사용 범위와 흐름](decisions.md#사용-범위와-흐름), #68 |
| 되살리기 페이지는 검색 색인에 넣지 않는다 | 다른 페이지의 내용을 모은 것이라 같은 내용이 두 번 잡힌다. MCP에서는 `get_page`로 읽는다 | [검색](decisions.md#검색), #68 |
| Thymeleaf로 만들고 그림 라이브러리를 쓰지 않는다 | 검증기와 같은 실행 환경 하나로 빌드·테스트한다. 화면 모양은 중요하지 않다 | [언어와 라이브러리](decisions.md#언어와-라이브러리) |

## 7. 부딪힌 문제와 해결

| 문제 | 해결 | 이슈 |
|---|---|---|
| 필드 타입의 "확인 안 됨"이 확인된 것처럼 보이고, 일부 값에 근거가 없었다. 엔드포인트가 없는 서비스에는 검증 범위가 없었다(PR 검토에서 발견) | 셋 다 고쳤다 | #28 |
| 근거 `파일:줄`이 글자뿐이라, 확인하려면 고정 커밋에서 파일을 직접 찾아야 했다 | 고정 커밋의 원본 줄과 응답 원문 페이지의 그 줄로 링크했다 | #39 |
| 근거가 여러 개인 값은 한 줄이 길어졌다(주문 서비스의 상품 요청 발행은 근거 7개) | 근거를 "근거 N개"로 접어 뒀다 | #39 |
| 확인됨, 확인 안 됨, 저장소에 근거 없음, AI 해석이 같은 모양이라 한눈에 갈리지 않았다 | 상태별 색으로 갈랐다 | #39 |
| 첫 화면의 확인 안 된 연결이 한 목록뿐이고 읽는 사람이 할 일이 없었다 | 이유 코드별로 묶고 묶음마다 할 일을 붙였다 | #60 |
| 통신 형식을 일반화한 뒤에도 첫 화면과 서비스 페이지의 문구가 Kafka로 남았다 | 메시지 목적지, 메시지 발행·구독, 메시지 연결로 바꿨다 | #70 |
| 외부 API(설정값 주소의 HTTP 호출)가 되살리기 페이지의 외부 자원 절에 나오지 않았다 | 외부 HTTP 호출(서비스·ID·종류·주소·경로)을 그 절에 더했다 | #70 |
| 첫 화면의 "확인 안 된 연결" 카드가 경고 수가 아니라 경고 묶음 수를 보였다 | 경고 수를 보이게 고쳤다 | #74 |
| 줄 중간의 근거·이유 접힘 표시가 닫혀 있어도 뒤 글자를 다음 줄로 넘겼다 | 모든 페이지에서 고쳤다 | #74 |

## 8. 한계

- 되살리기 페이지만 보고 대상을 실제로 띄울 수 있는지는 재지 않았다. SpartaHub 결과로 페이지가 내는 내용까지만 확인했다.
- 비교 실험은 MCP와 질의응답을 쟀다. 사람이 페이지를 읽고 답을 찾는 경우는 재지 않았다.
- 페이지는 검증 출력에 있는 것만 보여 준다. 추출하지 않은 사실은 나오지 않는다([추출 방식 7절](extraction.md#7-영역별-확인-정도)).
- 검증 출력이 바뀌면 서버를 다시 띄워야 한다.
- 대상이 바뀐 뒤 달라진 곳만 보여 주는 기능은 없다.

## 9. 개선할 수 있는 것

| 무엇 | 방법 | 비용 |
|---|---|---|
| 되살리기 페이지가 막힐 곳을 미리 보여 주는지 확인 | 4단계에서 HotDealWave를 띄우며 막힌 6곳([4단계 보고서 6절](reports/probe-hotdealwave.md#6-환경-준비))이 되살리기 페이지에 나오는지 하나씩 대조한다 | 유료 호출 없음. 이미 있는 기록과 페이지를 맞대 본다 |
| 되살리기 페이지만으로 띄우기 | 두 번째 대상을 이 페이지만 보고 띄우며 막힌 곳을 기록한다 | 대상의 DB와 외부 API 키를 직접 준비해야 한다 |
