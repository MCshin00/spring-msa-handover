7단계 완료. #33에서 본문을 `h2` 절 조각으로 색인하는 `search_docs`(BM25)와 `/api/search`, 도구 5개(`find_endpoint`, `trace_flow`, `find_subscribers`, `search_docs`, `get_page`)를 여는 `/mcp`를 더했다. Codex와 Claude Code에서 질문 하나씩으로 도구가 불리고, `requestProduct` 뒤의 "확인 안 됨"과 근거 `파일:줄`이 답에 그대로 전달되는 것을 확인했다. 다음 할 일: 8단계.

8단계 완료. #35에서 `/api/ask`(검색 상위 5개 → `gpt-6-luna` 한 번 → 인용 검사로 답·보류)와 검색·질문 페이지 `/search`를 더했다. 실제 호출 4번에서 필드 질문은 근거와 함께 답했고, 저장소에 없는 값은 보류했으며, `requestProduct` 수신자는 "확인 안 됨"으로 답했다. 남은 문제는 둘이다. 본문의 한국어가 AI 해석 항목에만 있어, 한국어로 물으면 코드 이름뿐인 흐름 절이 검색되지 않는다. 어노테이션이 없는 필드는 빈칸이라 모델이 다른 줄을 따라 지어낸다(추론 low·medium도 같음). #37에서 빈 필드를 "어노테이션 없음"으로 쓰고, 항목 종류 `설명`을 더해 업무 규칙 Skill이 엔드포인트·Kafka 발행·구독 94개에 한국어 설명을 썼다(AI 해석, 미확인). 설명은 페이지 맨 위 "설명" 절에 나오고, 모델에는 엔드포인트와 함께 토픽 페이지도 본문 전체를 넘긴다. Kafka 연결 경고의 이유는 식별자 나열에서 "같은 환경변수를 쓰는 구독을 찾지 못함, 토픽 값은 저장소 밖에서 정해짐" 문장으로 바꿨다. 실제 호출에서 couponId는 "검증 어노테이션 없음"으로, `requestProduct` 수신자는 "확인 안 됨"과 그 이유로 답했다(입력 1만에서 2만 토큰). #39에서 페이지를 꾸몄다. 근거 `파일:줄`은 접어 두고 고정 커밋 원본 줄·응답 원문 페이지로 링크하며, 흐름 단계는 상자·화살표로 잇고, 줄과 항목을 상태(확인됨·확인 안 됨·저장소에 근거 없음·AI 해석)별 색으로 가른다. 그림 라이브러리는 쓰지 않고, 검색·MCP·모델이 읽는 본문 글자는 꾸미기 전과 같다(전체 724개 절 대조). 6~8단계의 결과와 실제 호출·비용은 [서버 보고서](reports/server-hotdealwave.md)에 있다. 다음 할 일: 9단계.

MCP는 확인 안 된 것을 확인된 것처럼 말한 답이 없었고, 질의응답은 1개(Q01)였다. 맞음이 아닌 답 24개 가운데 13개는 문서에 그 내용이 없어서이고, 배포 워크플로·오류 응답 본문·페이지 직렬화 설정처럼 아직 추출하지 않은 것에 몰렸다. 질의응답은 검색에서 못 찾은 경우가 5개다. 다루는 범위는 근거 위치로 가르기로 했다. 결과와 원인은 [9단계 보고서](reports/eval-hotdealwave.md)에 있다. 다음 할 일: 추출 범위(배포 워크플로, 오류 응답 본문, 페이지 직렬화 설정, 모니터링 설정)와 질의응답 검색을 고친 뒤 10단계.

9단계 뒤 개선 완료. 9단계에서 문서에 없어 맞음이 되지 못한 내용을 추출 범위에 더했다. #47에서 오류 코드, 예외 처리기, Gateway 거부 응답, 페이지 직렬화 설정을 서비스 파일에, 엔드포인트에서 예외 생성 줄까지의 연결(`throws`)을 관계 파일에 더했다. 처리기 안에서 조건에 따라 값이 갈리면 "확인 안 됨"이다. #49에서 서비스 하나에 속하지 않는 배포 워크플로, 컨테이너 이미지, 메트릭 수집, 로그 전송, 모니터링 도구 설정을 `repository.json`과 `/repository` 페이지로 냈다. Secrets 값과 실행 환경 값, 모니터링 도구의 실행 정의는 "저장소에 근거 없음"이다. #51에서 이 형식을 도구 이름이 아닌 역할(배포 파이프라인, 컨테이너, 메트릭 수집, 로그 전송, 도구 자체 설정, 모니터링 도구)로 나눠, 다른 저장소의 도구도 같은 칸에 담게 했다. #53에서 질의응답 검색을 조정용 질문 8개(T03~T10, AI 초안을 최종 질문과 겹치지 않게 거른 뒤 개발자가 확정)로 조사했다. "받은 문서에서 빠뜨림"은 재현되지 않았다. 원인은 문서 용어 연결(핫딜 ↔ 타임세일), BM25의 표현 차이(HTTP 호출 ↔ Feign), 질문에 섞인 낱말로 좁혀지는 종류 거르기였다. 지시문 수정과 종류 말 수정은 효과가 없거나 다른 질문을 나쁘게 해 채택하지 않았다. 남긴 문제는 #53 댓글에 있다. 다음 할 일: 10단계. 시작할 때 대상의 통신 방식·기술을 도구 지원 범위와 대조하고, 서버에 고정된 대상 이름과 루트 `docker-compose.yml` 전제를 확인한다. 질의응답이 어디서 놓치는지 볼지(결정 기록은 두 번째 대상에 질문·채점을 하지 않는다)도 그때 정한다.

10단계 준비 중. #55에서 서버가 대상 이름·고정 커밋·근거 링크 주소를 분석 데이터(`target.json`)에서 읽게 했다. 두 번째 대상을 처음 쓰는 사람의 순서로 쓰도록 점검해 고칠 곳을 찾았다. 대상을 서브모듈 대신 작업 폴더로 받고, 서버가 대상마다 따로 뜨게 하는 것 등이다. 두 모델의 독립 설계안, 교차 비판, 별도 판정을 거쳐 [사용 범위와 흐름](decisions.md#사용-범위와-흐름)를 정했다. #56에서 대상을 작업 폴더로 떼어 냈다. `init`이 대상을 작업 폴더에 복제해 커밋을 고정하고 AI 세션용 지시 파일을 쓰며, AI가 `verify`로 검증 출력을 만들고 사람이 `serve`로 띄운다. HotDealWave는 결과와 검증 출력을 커밋한 예시 작업 폴더(`examples/hotdealwave`)가 됐고, 옮기기 전후 페이지 본문은 응답 근거 경로 말고 같다. #58에서 형식을 바꾸지 않고 흔한 Spring MSA 구성을 읽게 했다. 하위 폴더의 Maven·Kotlin DSL 모듈, `properties`·`yaml` 설정, 위치가 다른 compose 파일과 맵 형식 `environment`, 기본값 있는 환경변수, 같은 토픽 이름의 Kafka 연결, Java DSL 경로와 `StripPrefix`, Spring Security `permitAll`, record와 `@JsonProperty`다. 필드의 `@JsonProperty`·`@JsonNaming`을 무시하고 getter 이름을 "확인됨"으로 내던 문제와, 앞부분 일치가 아닌 인증 필터에서도 토큰 판정을 "확인됨"으로 내던 문제를 함께 고쳤다. HotDealWave 예시의 검증 출력은 그대로다. #60에서 경고마다 이유 코드와 할 일을 붙여 첫 화면을 이유별로 묶고(예시 13개는 저장소 밖 값 9, 저장소 안에서 잇지 못함 4), 배열마다 "확인됨"의 뜻을 페이지 범례와 MCP 결과 머리에 뒀다. 페이지는 확인되지 않은 값에만 상태와 접은 이유를 붙인다. 응답 비교를 `verify`로 옮겨 응답 확인이 서비스 파일을 고치지 않는 관찰 기록이 됐고(예시 비교 결과는 Python 스크립트와 같다), 형식에 자리가 없는 방식은 `unsupported`로 남아 서비스 페이지와 흐름 결과에 나온다. README에 다른 구성에 맞추려면 고칠 곳 표를 뒀다. 다음 할 일: SpartaHub 시험 → 질의응답 하이브리드 검색 → 되살리기 페이지.


#62에서 서비스 간 통신 형식을 역할 배열과 `kind`로 일반화했다. OpenFeign·RestTemplate·RestClient·WebClient·HTTP 인터페이스, Kafka·RabbitMQ·Spring Cloud Stream을 다루고, 선언 줄 규칙은 `CommunicationRules` 한 곳에 있다. HotDealWave 예시는 배열 이름과 `kind`만 옮겼고 상태 수와 경고 13개가 그대로다. #66에서 SpartaHub 시험(#54)에서 찾은 결함을 고쳤다. 매핑의 경로 인자만 읽고, 추출의 `external`을 보존하며, 허용 목록 메서드가 비어도 멈추지 않는다. 추출 지시문은 서비스 수와 함께 동시·순차 실행을 묻는다. SpartaHub 재검증에서 경고는 52개에서 35개로 줄고, 확인된 내부 호출 대상은 2개에서 19개로 늘었다.

#63에서 질의응답(`/api/ask`)의 검색을 BM25와 임베딩(`text-embedding-3-large`)의 RRF로 바꾸고, 모델에 넘기는 조각을 상위 8개로 늘렸다. `/api/search`와 `search_docs`는 BM25 상위 5개 그대로다. 조정용 질문 T03~T10에서 BM25와 결과가 갈린 절을 Codex·Opus가 따로 판정하고, 갈린 판정은 개발자가 정했다. 5칸 RRF는 T03의 근거 2개를 잃어 채택 기준을 채우지 못했다. 8칸 RRF는 새 근거 13개를 찾고 잃은 근거가 없어 채택했다. 판정 기록은 PR #65 댓글에 있다. 최종 질문으로 질의응답을 다시 돌려 9단계 방식으로 채점했다. 9단계(맞음 6·부분 11·틀림 4)와 비슷한 맞음 5·부분 11·틀림 5다. 답한 12개에는 틀림이 없고, 틀림은 모두 보류다. 결과는 [9단계 보고서 9절](reports/eval-hotdealwave.md#9-질의응답-검색을-바꾼-뒤-다시-잰-결과63)과 `eval/results/final-rrf8/`에 있다.

#68에서 되살리기 페이지(`/revival`)를 더했다. 외부 자원, 채워야 할 환경변수(이름별로 묶음), 저장소 밖 비밀값, 컨테이너, 띄울 때 확인할 연결(경고 이유별 할 일), 운영 함정, 도구가 다루지 않은 위치를 검증 출력에서 모은다. 모든 절이 다른 페이지의 반복이라 검색·질의응답 색인에서는 빼고 MCP `get_page`로 읽는다. 

10단계 완료. 고친 Skill로 SpartaHub를 처음부터 다시 추출했다. 서비스 10개를 하위 에이전트로 동시에 추출하고 업무 규칙·함정까지 약 47분 걸렸다. 경고는 첫 시도 52개에서 16개(추출 잘못 7, 실제 코드 3, 도구가 모름 6)로 줄고, 확인된 내부 호출 대상은 20개, 업무 규칙·함정·설명은 171개다. 결함 두 가지의 원인이 개발 규칙이 Spring 어노테이션의 정의까지 막은 것이라, AGENTS.md에 "대상이 쓰는 Spring 기능은 고정 커밋에 나오지 않은 속성·형태까지 그 기능의 정의대로 읽는다"를 더했다. 되살리기 페이지로 실제 대상을 띄우는 측정은 하지 않았다. 결과는 [10단계 보고서](reports/general-msa-spartahub.md)에 있다. 다음 할 일: 보고서 7절의 남은 과제 중 고칠 것을 고르는 일, README 재구성.

#70에서 첫 화면·서비스 페이지의 Kafka 문구를 메시지로 바꾸고(메시지 목적지, 메시지 발행·구독, 메시지 연결), 되살리기 페이지의 외부 자원 절에 외부 HTTP 호출(서비스·ID·종류·주소·경로)을 더했다.

#71에서 `init` 완료 안내와 README가 AI 세션에 "지시 파일대로 끝까지 해 줘"라고 하게 바꿨다("추출해 줘"만으로는 세션이 업무 규칙·함정 단계 전에 멈췄다). `relations.json` 없이 `verify`를 부르면 오류 스택 대신 관계 단계를 먼저 하라는 한 줄로 끝난다.
